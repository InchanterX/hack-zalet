# Промпты и принятые решения

Работа над моделью данных с ИИ-ассистентом (Claude Code): какие запросы ему давались и что в итоге решили. Промпты восстановлены по смыслу и слегка отредактированы, порядок сохранён.

Результат лежит в этой папке:

| Файл | Что внутри |
|---|---|
| `core.sql` | Сборка модели `core` из `raw` |
| `mart.sql` | Ответы на вопросы 1–5 (`mart.q01`–`q05`) |
| `checks.sql` | Проверка ответов по контрольным цифрам из `tasks.md` |
| `load_raw_psql.sql` | Загрузка `raw` без Python |
| `build.sh` | Сборка одной командой |

Сборка с нуля:

```bash
bash izotov/build.sh              # raw уже загружен через scripts/setup.sh
bash izotov/build.sh --load-raw   # сначала загрузить raw из data/*.csv
```

## 1. Разобраться в слоях raw / core / mart

**Промпт.**
> Что требуется сделать с raw-данными? Что такое витрины, как в них располагать ответы на вопросы и чем витрина отличается от core-слоя? Что можно сделать в core, кроме приведения типов?

**Решения.**
- **raw не меняем.** Вся работа идёт при переносе в core: изучить данные, привести типы (пустую строку — в `NULL`), почистить, убрать дубли и сверить результат с raw.
- **core — модель предметной области.** Здесь один раз решается то, что иначе каждый аналитик решал бы по-своему: ключи, связи, правило «что считается выручкой», кто такой покупатель. Иначе отчёты продолжат давать разные цифры.
- **mart — ответы и витрины поверх core, никогда поверх raw.** Каждому вопросу — своё представление `mart.qNN_*`. Доли и средние в витринах хранятся как числитель и знаменатель: их нельзя складывать по срезам.

## 2. Спроектировать core по реальным данным

**Промпт.**
> Предложи максимально практичную модель данных core.

**Как работали.** Прежде чем проектировать, проверили на базе, какие ключи действительно уникальны, где «грязь» и как определяется выручка. Python на машине был недоступен, поэтому `raw` загрузили через `psql \copy` внутри контейнера: все 550 759 строк на месте.

**Что выяснили по данным:**
- **Отзывы.** Ни `review_id`, ни `order_id` в `order_reviews` по отдельности не уникальны, уникальна только пара. У 547 заказов несколько отзывов.
- **Покупатели.** `customer_id` уникален для каждого заказа: 99 441 значение. Настоящий покупатель — `customer_unique_id`: 96 096 человек.
- **Позиции.** Одна строка `order_items` — одна единица товара. Три одинаковых товара в заказе — это три строки с `order_item_id` 1, 2, 3.
- **Выручка и средний чек.** Выручка = `sum(price)` по заказам со статусом `delivered` = 13 221 498.11, доставка в неё не входит. Средний чек = `price + freight` по заказу целиком = 159.88. Отсюда решение хранить цену и доставку раздельно.
- **Повторные покупатели.** Вернувшийся — тот, у кого больше одного заказа в любом статусе: 3,12%, совпадает с контролем. Если считать только `delivered`, выходит 3,00%.
- **Категории.** У 610 товаров нет категории. Две категории (`pc_gamer`, `portateis_cozinha_e_preparadores_de_alimentos`) отсутствуют в справочнике перевода.
- **Почтовые индексы.** У части индексов потерян ведущий ноль: длина 4–5 символов.
- **Прочая «грязь»:**

| Что | Сколько |
|---|---|
| Заказы без позиций | 775 |
| Заказ без платежа | 1 |
| `delivered`, но нет даты вручения | 8 |
| Сумма платежей ≠ сумме позиций | 366 |
| Тип платежа `not_defined` | 3 |
| Рассрочка 0 | 2 |

**Решения — «звезда» с явным зерном:**
- **Факты:**
  - `fact_order` — заказ;
  - `fact_order_item` — одна единица товара, ключ `(order_id, order_item_id)`;
  - `fact_payment` — платёж, ключ `(order_id, payment_sequential)`;
  - `fact_review` — пара `(review_id, order_id)`, флаг `is_latest_for_order`.
- **Справочники:**
  - `dim_customer` — по `customer_unique_id`;
  - `dim_seller`, `dim_product`;
  - `dim_category` — со строкой `unknown`;
  - `dim_order_status` — с флагами `is_revenue`, `is_cancelled`, `is_final`;
  - `dim_date` — календарь.
- **Итоги заказа считаются в `fact_order` один раз:**
  - суммы цен, доставки и платежей;
  - число единиц и строк заказа;
  - сроки доставки и признак опоздания;
  - номер заказа у покупателя.
- **Строки заказа** — разные пары товар × продавец, **единицы** — `count(*)`. Только так в вопросе 3 два средних отличаются друг от друга.
- **Странные строки не удаляются.** Они помечаются флагами `dq_*` и записываются в журнал `core.dq_issue`.

## 3. Реализовать модель и ответы

**Промпт.**
> Внеси изменения в код.

**Решения.**
- **`core.sql` пересоздаёт схему с нуля**, поэтому скрипт можно запускать сколько угодно раз. Типы приводятся явно, у всех таблиц объявлены первичные ключи, проверки допустимых значений (`CHECK`) и связи.
- **`mart.sql`: пять представлений `q01`–`q05`**, все читают только core.
  - **Вопрос 1.** Месяцы берутся из календаря, поэтому ноябрь 2016 попадает в отчёт с нулём. Число заказов — заказы, вошедшие в выручку. Все оформленные — в отдельной колонке `all_orders_cnt`.
  - **Вопрос 2.** Выручка продавца считается по позициям, поэтому в заказе с несколькими продавцами каждый получает только свои товары.
  - **Вопрос 5.** Товары без категории попадают в `unknown`, поэтому сумма по категориям равна общей выручке.
- **В конце сборки — сверки с raw:** число строк, суммы денег, потери на соединениях со справочниками. При расхождении сборка падает.

Все пять контрольных цифр из `tasks.md` сошлись.

## 4. Проверить модель по критериям оценки

**Промпт.**
> Проверь, что модель выполняет критерии.
> 2 этап, качество модели: гранулярность фактов, работа с ключами, пропуски и статусы, структура и наполнение справочников.
> 3 этап, поддерживаемость: единообразие, самопроверки, воспроизводимость сборки, прозрачность решений.

**Что нашли при проверке и что поменяли:**

| Критерий | Что было не так | Решение |
|---|---|---|
| Гранулярность | Зерно таблиц записано только в комментариях SQL-скрипта | Зерно записано в описании каждой таблицы прямо в базе (`COMMENT ON TABLE`): видно в DBeaver и через `\d+` |
| Ключи | Связи проверялись построчно при вставке: медленно | Связи объявляются после загрузки одним проходом. «Сирота» по-прежнему роняет сборку, но уже с именем нарушенной связи |
| Пропуски и статусы | Неизвестный статус не отличался от известных | Флаг `is_known` в справочнике статусов. Такой статус попадает в журнал проблем и не может считаться выручкой |
| Справочники | Способ оплаты хранился свободным текстом | Новый справочник `dim_payment_type`. `not_defined` — отдельная строка с флагом `is_defined = false` |
| Единообразие | `price`, `freight_value`, `payment_value` выпадали из правила имён | Одно соглашение по всему слою: `*_at`, `*_date`, `*_amt`, `*_cnt`, `is_*`, `has_*`, `dq_*`. Записано в шапке `core.sql` |
| Самопроверки | Только сверка строк и сумм | 7 сверок в `core.sql`: строки, деньги, соединения, «у покупателя ровно один первый заказ», «у заказа один последний отзыв», «выручку дают только известные статусы», «нет заказов с выручкой без позиций». Плюс `checks.sql` с 11 контрольными цифрами |
| Воспроизводимость | Сборка в два ручных шага, загрузка raw зависела от Python | `build.sh`: core → mart → проверки одной командой. `--load-raw` загружает raw через psql |
| Прозрачность | Решения были разбросаны по комментариям | `DECISIONS.md` (полстраницы) и описания ключевых колонок в базе |

**Что ещё сделали:**
- **Ускорили сборку core со 100 до 13 секунд.** Три `UPDATE` поверх `fact_order` (около 49 с) заменили одной вставкой, в которой итоги заказа считаются сразу. Полная сборка от CSV до проверок занимает около 35 секунд.
- **Проверили, что самопроверка действительно ловит ошибку.** Подставили в вопрос 3 «типичный неверный ответ» 123.75 из `tasks.md` — `checks.sql` упал с `FAIL`. Затем модель пересобрали начисто.
- **Уточнили число заказов с датами не по порядку: 189, а не 166.** Теперь проверяются четыре условия, а не два: добавились «оплачен раньше оформления» и «вручён раньше передачи в доставку».

**Итог журнала `core.dq_issue`:**

| Проблема | Сколько |

| `no_category` — товар без категории | 610 |
| `amount_mismatch` — сумма платежей ≠ сумме позиций | 366 |
| `dates_inconsistent` — даты не по порядку | 189 |

## От чего отказались и почему

- **От суррогатных ключей.** Естественные ключи источника стабильны, а без истории изменений суррогаты ничего не дают. Понадобятся вместе с историчностью справочников.
- **От удаления «грязных» строк.** Удалённое не объяснить на защите и не сверить. Помеченное видно и считается.
- **От хранения готовых долей и средних в витринах.** Их нельзя складывать по срезам. Храним числитель и знаменатель.
- **От историчности справочников.** В выгрузке нет истории изменений продавцов и товаров. Это следующий шаг развития модели.
