## 2026-10-28 — этап A1: окружение и пайплайн

Сгенерировано: `.gitattributes`, `.gitignore`, `.env.example`, `tools/Dockerfile`, `compose.pipeline.yml`, `data.sha256` (значения из PLAN 6.6), `data.rows`, `inject/README.md`, `model/build.sql`, `model/00_reset.sql`, `run.sh` (стадии `preflight`, `up`, `data`, `raw`, `build`, команды `psql`, `--reset`, `--force-raw`); объекты БД: схемы `core`, `mart`, `meta`, `ops`, таблица `ops.raw_state`.

Решения агента:
- `ops.raw_state` создаётся в `run.sh` (стадия `raw`), а не в `model/`: это состояние пайплайна, сборка от него не зависит.
- Перед загрузкой `raw` строка `ops.raw_state` удаляется отдельной транзакцией: если загрузка или патч упадут, следующий запуск перезальёт `raw` даже при `--force-raw` с теми же входами.
- `--reset` выполняется внутри стадии `raw` (DROP своей базы перед созданием), отдельной стадии нет. Удаление и создание запрещены для `postgres`, `template0/1`, `marketplace`, `hack` — и в `preflight`, и в самой стадии.
- Сравнение строк с `data.rows` при непустом `inject/` — warning, без патчей — error (код 40).
- `compose.pipeline.yml`: `init: true` (tini), чтобы SIGTERM от `docker stop` доходил до bash и psql.
- Проверка CRLF сделана через `tr`, а не `grep $'\r'`: внутри `$(...)` Git Bash превращает `$'\r'` в пустой шаблон, и grep совпадал с любым файлом (найдено на первом прогоне).
- `./run.sh psql` возвращает код самого psql, а не код из таблицы 6.15.

Проверено (всё запускалось на Windows 11 + Git Bash + Docker Desktop 28.5.2):
- `docker compose config` с нашим файлом и без → проект `hack-zalet` в обоих случаях, сервис `postgres` идентичен; `docker compose up -d --dry-run postgres` (compose организаторов) → `Container hack_postgres Running`, без пересоздания.
- `model/build.sql` во временном postgres:16 без параметров и с параметрами, дважды подряд → rc 0, схемы и комментарии созданы.
- `./run.sh preflight` → rc 0; с CRLF в `../scripts/setup.sh` (временно, восстановлен) → rc 10 с инструкцией; `SOLUTION_DB=marketplace` в `.env` → rc 10.
- `./run.sh up` без контейнера → создан `hack_postgres` и том `hack-zalet_pgdata`, healthy за 7 с; повторно → «пропуск».
- `./run.sh data` → скачано 8 файлов, все хэши из PLAN 6.6 совпали; повторно → пропуск; дописанный байт в `olist_sellers_dataset.csv` (оригинал восстановлен) → rc 30 и имя файла.
- `./run.sh raw` → 550 759 строк, совпадение с `data.rows`; повторно → пропуск по отпечатку; неверный `data.rows` → rc 40, отпечаток не записан, следующий запуск перезалил; временный патч в `inject/` → перезаливка, warning «3096 вместо 3095», патч записан в `ops.raw_state.inject`; упавший патч (`1/0`) → rc 40, отпечаток не записан, после удаления патча — перезаливка.
- `./run.sh build` → rc 0; временная синтаксическая ошибка в `model/` → rc 50, таблица-маркер в `core` пережила откат; временный `RAISE EXCEPTION 'CHECK FAILED: …'` → rc 55; открытая транзакция с блокировкой на таблице `core` → `lock timeout` через 10 с, rc 50, модель не тронута.

- `./run.sh --reset` (наш образ перед этим удалён) → rc 0 за 8 с; в списке баз сменился только `oid` базы `inchanterx`; проверочная база «коллеги» с таблицей не тронута (удалена после проверки); `marketplace` — те же схемы и объекты, `raw.orders` = 0 строк, как было.
