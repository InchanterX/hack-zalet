## 2026-10-28 — этап A1: окружение и пайплайн

Сгенерировано: `.gitattributes`, `.gitignore`, `.env.example`, `tools/Dockerfile`, `compose.pipeline.yml`, `data.sha256` (значения из PLAN 6.6), `data.rows`, `inject/README.md`, `model/build.sql`, `model/00_reset.sql`, `run.sh` (стадии `preflight`, `up`, `data`, `raw`, `build`, команды `psql`, `--reset`, `--force-raw`); объекты БД: схемы `core`, `mart`, `meta`, `ops`, таблица `ops.raw_state`.

Решения агента:
- `ops.raw_state` создаётся в `run.sh` (стадия `raw`), а не в `model/`: это состояние пайплайна, сборка от него не зависит.
- Перед загрузкой `raw` строка `ops.raw_state` удаляется отдельной транзакцией: если загрузка или патч упадут, следующий запуск перезальёт `raw` даже при `--force-raw` с теми же входами.
- `--reset` выполняется внутри стадии `raw` (DROP своей базы перед созданием), отдельной стадии нет. Удаление и создание запрещены для `postgres`, `template0/1`, `marketplace`, `hack` — и в `preflight`, и в самой стадии.
- Сравнение строк с `data.rows` при непустом `inject/` — warning, без патчей — error (код 40).
- `compose.pipeline.yml`: `init: true` (tini), чтобы SIGTERM от `docker stop` доходил до bash и psql.
- Проверка CRLF сделана через `tr`, а не `grep $'\r'`: внутри `$(...)` Git Bash превращает `$'\r'` в пустой шаблон, и grep совпадал с любым файлом (найдено на первом прогоне).
- `./run.sh psql` возвращает код самого psql, а не код из таблицы 6.15.

## 2026-10-28 — этап A: .gitattributes, проверка свежим клоном, исправление --no-deps

Сгенерировано: бинарные шаблоны в `.gitattributes`; `require_postgres` и флаг `--no-deps` в `run.sh`; пояснение в PLAN.md, 6.3.

Решения агента:
- `.gitattributes`: `* text=auto eol=lf`, бинарные форматы (картинки, pdf, архивы, xlsx, parquet, duckdb) — `binary`. `git add --renormalize inchanterx/` изменений не дал: все 14 файлов уже хранились с LF.
- **Найденный дефект:** `docker compose run` поднимает зависимости и при расхождении конфигурации `postgres` пересоздаёт общий контейнер `hack_postgres`. Обнаружено `docker compose --dry-run … run` из свежего клона (другие абсолютные пути bind mount → `Container hack_postgres Recreate`). То же произошло бы в основном репозитории после `sync`, если организаторы изменят `docker-compose.yml`. Исправление: стадии и `psql` запускаются с `--no-deps`, готовность `postgres` проверяет `run.sh` (не healthy → код 20, контейнер не трогается); поднимает контейнер только стадия `up`.
- Клон для проверки положен в папку с тем же именем корня (`…/clonetest/hack-zalet`): имя compose-проекта берётся из имени папки, а `container_name: hack_postgres` у организаторов фиксирован — клон в папке с другим именем упёрся бы в конфликт имени контейнера (допущение «один клон на машину», PLAN 6.3). В `.env` клона — `SOLUTION_DB=inchanterx_clonetest`, чтобы `--reset` клона не удалил рабочую базу.

Проверено:
- `git clone -c core.autocrlf=true` во временную папку → наши 14 файлов `w/lf`, файлы организаторов (`scripts/`, `docs/`, `docker-compose.yml`, `README.md`, `.gitignore`) — `w/crlf`.
- `docker compose --dry-run … run --rm -T pipeline true` из клона → `Container hack_postgres Recreate`; с `--no-deps` → строк о контейнере нет.
- `./run.sh --reset` в клоне как есть → rc 10: `preflight` остановился на CRLF в `../scripts/*.sh`, `load_raw.py` с инструкцией (это ожидаемое поведение по PLAN 6.3: наш `.gitattributes` на файлы организаторов не распространяется, а менять их нельзя).
- Инструкция из сообщения выполнена в клоне (`git config core.autocrlf input`, повторная выгрузка `scripts/`; `git status` после — пусто) → `./run.sh --reset` rc 0 за 30 с: 8 CSV скачаны заново, хэши совпали, 550 759 строк, сборка прошла.
- После прогона из клона: в списке баз добавилась только `inchanterx_clonetest`; `hack_postgres` не пересоздан (время создания 09:34:11 UTC не изменилось); `ops.raw_state.loaded_at` базы `inchanterx` не изменился. Клон и его база удалены.
- `--no-deps` в основном репозитории: `./run.sh build`, `./run.sh psql` → rc 0; `docker stop hack_postgres` → `./run.sh build` rc 20 «не запущен», контейнер остался `exited`; `./run.sh up` → `Starting`/`Healthy` (запуск существующего контейнера, без пересоздания).

Не проверялось:

- **CI** — workflow не создавался (этап C), прогона на `ubuntu-latest` не было.

Требует проверки человеком: `--no-deps` — отступление от буквы PLAN 6.3 (там была опора на `depends_on`), PLAN обновлён; команде стоит подтвердить.
