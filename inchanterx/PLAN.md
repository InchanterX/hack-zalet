# PLAN.md — модель данных Capibara (raw → core → mart)

Документ для передачи в Claude Code. Описывает **что** строим и **почему**, а не готовый код.
Все цифры ниже получены профилированием полной выгрузки (8 CSV, 550 759 строк).

Расположение: корень форка — оригинальный репозиторий организаторов; наше решение целиком в папке `inchanterx/` (другие участники делают альтернативные решения в своих именных папках). Пути вида `model/…` даны относительно `inchanterx/`, файлы организаторов — от корня (`../scripts/…`). Подробно — раздел 6.1.

---

## 0. Контекст и границы

- Организаторы дали `scripts/setup.sh`: он поднимает `postgres:16-alpine`, создаёт схемы `raw/core/mart` и грузит CSV в `raw` базы `marketplace` (все колонки `text`, пустое значение без кавычек → `NULL`). Мы **переиспользуем** их контейнер и загрузчик (`../scripts/load_raw.py`, `../scripts/download_data.sh`), но грузим в **свою базу** `inchanterx` и оборачиваем всё в собственный пайплайн (раздел 6).
- Корень форка не меняем (`scripts/`, `docs/`, `docker-compose.yml`), чужие именные папки — тоже. Тогда `git merge upstream/main` в середине хакатона пройдёт без конфликтов, а решения участников не мешают друг другу. Всё наше — в `inchanterx/`; единственное исключение — workflow CI в `.github/workflows/inchanterx.yml`.
- Схему `raw` не меняем. Её перезаливает только загрузчик организаторов (или их «вброс»).
- Сборка модели **не** кладётся в `docker-entrypoint-initdb.d`: init-скрипты выполняются до загрузки `raw` и только на пустом volume.
- Интерфейс не делаем. Ответы — SQL-представления в `mart` + выгрузка цифр в `answers/`.
- PostgreSQL **16**: используем его возможности (`pg_input_is_valid`, `UNIQUE NULLS NOT DISTINCT`).
- Единственная точка входа — `inchanterx/run.sh` (на хосте нужны только `bash`, `git`, Docker с Compose v2). Хост может быть Windows (Git Bash + Docker Desktop): особенности такого хоста — раздел 6.3, «Хост на Windows».
- Окружение организаторов берём **как есть**: их compose, порт, healthcheck и скрипты загрузки — данность, а не предмет нашей работы. Мы не обходим их особенности, а надстраиваем своё поверх.

### 1.3 Неочевидные места (каждое — пункт записки и вопрос защиты)

1. **Дубли позиций = количество.** Внутри (order, product, seller) все повторы имеют одинаковые price/freight/shipping_limit. Уникальных пар (order, product): 102 425 из 112 650 строк. Средне на доставленный заказ: 1.0385 различных товаров, 1.1422 единицы.

3. **Отзыв ↔ заказ — многие-ко-многим.** Один `review_id` висит на нескольких заказах (всегда одного и того же `customer_unique_id`, содержимое идентично). У 547 заказов несколько отзывов, у 202 из них оценки различаются.
4. **Категории:** 610 товаров без категории (у них же пусты name/description/photos); 2 категории без перевода: `pc_gamer` (3 товара), `portateis_cozinha_e_preparadores_de_alimentos` (10). Итого 71 + 2 + «неизвестная» = **74** (совпадает с контролем).
5. **Почтовые индексы потеряли ведущий ноль** (длина 4–5) → нормализовать `lpad(…, 5, '0')`.
6. **Грязные города продавцов:** `sao paulo / sao paulo`, `sbc/sp`, `4482255`, `rio de janeiro \rio de janeiro`… Сохраняем как есть + флаг качества (чистка города — вне рамок, но упомянуть в стратегии).
7. **Хронология:** 1 359 заказов «переданы в доставку» раньше подтверждения оплаты (432 — больше чем на сутки); 166 — раньше оформления; 23 — вручены раньше передачи в доставку; 74 отзыва созданы раньше оформления заказа.
8. **Статус vs даты:** 8 `delivered` без даты вручения, 14 `delivered` без `approved_at`, 6 `canceled` с датой вручения, 2 `delivered` без даты передачи перевозчику.
9. **Платежи:** `not_defined` (3 строки, сумма 0), voucher с суммой 0 (6), credit_card с `installments = 0` (2). Сумма платежей ≠ сумма позиций у 366 заказов (269 больше, 97 меньше).
10. **`shipping_limit_date` в 2020 году** — 4 позиции (выброс).
11. `order_estimated_delivery_date` всегда 00:00:00 → тип `date`. `review_creation_date` — 85 значений не в полночь → оставляем `timestamp`.
12. 252 покупателя (`customer_unique_id`) заказывали на разные адреса → адрес — свойство заказа, а не человека.
13. Ноябрь 2016 — ноль заказов; сентябрь–октябрь 2018 — 20 заказов, ни одного delivered.
14. **Одновременные заказы.** В 290 случаях один покупатель оформил несколько заказов в одну и ту же секунду — по сути одна корзина, разбитая на заказы. Из 2 997 «вернувшихся» покупателей (контроль Q4) у 257 все заказы оформлены в одну секунду, у 848 — в один день. Повторная покупка в другой день — 2.24 %, а не 3.12 %. Контроль Q4 считает по заказам — это определение организаторов, но для дашборда и защиты важно знать разницу.

### 1.4 Расшифровка контрольных цифр (все пять сходятся)

| Вопрос | Определение, дающее контроль |
|---|---|
| Q1 выручка | `sum(price)` (**без доставки**) по позициям заказов со статусом `delivered`, месяц = месяц `order_purchase_timestamp`, календарь 2016-09…2018-08 (24 мес., 2016-11 = 0) → **13 221 498.11** |
| Q2 продавцы | то же определение выручки на уровне позиции; топ-1: `4869f7a5…`, guariba/SP, 1 124 заказа, 1 148 единиц, **226 987.93** |
| Q3 средний чек | `sum(price + freight) / count(distinct order)` по delivered → **159.88** (чек **с доставкой**). 139.97 = среднее по позиции с доставкой; 123.75 — вариант «средняя цена позиции» |
| Q4 покупатели | ключ `customer_unique_id`, заказы **всех статусов**: 96 096, вернулись 2 997 → **3.12 %** (по delivered было бы 93 358 / 3.00 %) |
| Q5 категории | delivered, `price`, 74 категории с явной «неизвестной», топ — `health_beauty` **1 233 131.72**, сумма = 13 221 498.11 |

**Вывод для модели:** у организаторов «выручка» = товары без доставки, «чек» = товары + доставка, «покупатель» = любой оформивший заказ. Это три разных показателя. В модели они должны существовать **раздельно и явно названы** (`goods_amount`, `freight_amount`, `order_total`), а правило «что считается выручкой» — жить в одном месте (справочник статусов), а не в каждом запросе. Это главный пункт записки о решениях.

## 2. Архитектура слоёв

```
raw   (дано, не трогаем)
  │  типизация, нормализация, дедупликация, отбраковка с логом
  ▼
core  (нормализованная модель: справочники + сущности + факты на своих зёрнах)
  │  агрегаты на уровне заказа, ответы
  ▼
mart  (order_summary + view на каждый вопрос)

meta  (журнал сборки, отбракованные строки, лог проблем качества, результаты самопроверок)
ops   (состояние пайплайна: отпечаток загруженного raw; сборкой не пересоздаётся)
```

Схему `meta` создаём сами в сборке (пересоздаётся каждый раз), схему `ops` — один раз (`CREATE SCHEMA IF NOT EXISTS`), её пишет стадия `raw` пайплайна.

## 3. Схема `core`

### 3.1 Общие соглашения

- **ID источника → `uuid`.** 16 байт вместо 33 у text, быстрее сравнение и индексы, плюс встроенная валидация формата. Натуральные ключи оставляем ключами: суррогаты для неизменяемых сущностей без историчности ничего не дают, а модель становится труднее объяснить. Суррогатные `smallint` — только у справочников, где натурального ключа нет или он «грязный» (категория с NULL).
- **Деньги → `numeric(12,2)`.** Только точный тип: контрольные суммы сверяются до копейки, float даст дрейф.
- Счётчики/габариты → `smallint` / `integer`. Даты-моменты → `timestamp` (без tz: в источнике локальное время Бразилии, зона не указана — фиксируем в записке). В Бразилии в 2016–2018 годах действовал летний переход времени и несколько часовых поясов, поэтому длительности могут ошибаться на час; показатели считаются в днях, и это допустимо.
- **Формат ID на выходе.** `uuid` в Postgres всегда выводится с дефисами (`4869f7a5-dfa2-77a7-…`), а в источнике и в условии ID без дефисов. Во всех ответах, выгрузках и представлениях `mart` ID выводятся в исходном виде через функцию `core.fmt_id(uuid) → text` (`replace(id::text, '-', '')`). Иначе ответ на Q2 не совпадёт с источником при сверке.
- **Округление — только на выходе.** В `core` и `order_summary` значения не округляются. В представлениях ответов: деньги — `round(x, 2)`, проценты — `round(100.0 * a / b, 2)`. Все доли считаются в `numeric`, без целочисленного деления.
- **Детерминизм.** Любая оконная функция и любой `DISTINCT ON` получает полный порядок до уникального ключа: `customer_order_seq` — по (`purchase_ts`, `order_id`) (290 пар заказов одного покупателя с одинаковым `purchase_ts`); последний отзыв — по (`created_ts`, `answered_ts`, `review_id`); выгрузки — `ORDER BY` по уникальному ключу. Две сборки на одних данных обязаны дать побайтно одинаковые выгрузки ответов.
- **Справочные сиды, написанные агентом** (названия и регионы штатов, описания статусов, описания кодов проблем), — это факты из знаний модели, а не из данных. У таких таблиц колонка `source = 'manual'`, и в `docs/AI_LOG.md` они отмечаются как требующие проверки человеком.
- Пустые строки и пробелы → `NULL` (`nullif(btrim(x), '')`) для всех текстовых полей.
- **Безопасное приведение типов через `pg_input_is_valid(value, 'type')`** (PG16): `CASE WHEN pg_input_is_valid(x,'timestamp') THEN x::timestamp END`. Без PL/pgSQL-исключений, без подтранзакций, быстро. Если исходное значение не NULL, а результат NULL — пишем в `meta.dq_issue`. Мусор во «вбросе» не уронит сборку.
- Именование: snake_case, таблицы в единственном числе, `_ts` — timestamp, `_date` — date, `_amount` — деньги, `is_`/`has_` — boolean.
- Таблица заказов — `core.customer_order`, алиас `o`. Имя без зарезервированного слова `order` (кавычки нигде не нужны) и в паре с `seller_shipment` читается однозначно: заказ покупателя целиком и часть этого заказа у одного продавца. Колонка-ключ по-прежнему `order_id` — как в источнике.
- `COMMENT ON TABLE/COLUMN` для каждой таблицы и каждой неочевидной колонки: зерно, источник, правило. Это прозрачность модели и подсказка аналитикам в DBeaver.

### 3.2 Справочники

**`core.order_status`** — зерно: статус.
`status_code text PK`, `description text`, `stage_order smallint` (created→approved→invoiced→processing→shipped→delivered; canceled/unavailable отдельно), `is_final bool`, `is_revenue bool` (только delivered = true), `is_cancelled bool`, `is_known bool`.
Наполнение: seed из 8 известных статусов с описаниями + `INSERT … SELECT DISTINCT` новых статусов из raw с `is_known = false`, `is_revenue = false` и warning в лог. Правило выручки живёт **здесь и только здесь**.

**`core.payment_type`** — `payment_type_code text PK`, `description`, `is_known`. Seed + автодобавление неизвестных (как у статусов). `not_defined` — валидный код с пометкой.

**`core.product_category`** — зерно: категория.
`category_id smallint PK` (суррогат), `name_pt text UNIQUE NULLS NOT DISTINCT` (PG15+), `name_en text NOT NULL`, `is_unknown bool`, `has_translation bool`.
Наполнение: все категории из `raw.products` ∪ из `raw.product_category_translation`; для непереведённых `name_en = name_pt`, `has_translation = false`; одна строка `is_unknown = true` (`name_pt = NULL`, `name_en = 'unknown'`). Итого 74. У товара `category_id NOT NULL` — ни один товар не теряется на JOIN.

**`core.state`** — `state_code char(2) PK`, `state_name`, `region` (Norte/Nordeste/Centro-Oeste/Sudeste/Sul). Seed 27 штатов. Регион пригодится в срезах дашборда и вопросах второй половины. Неизвестный код из raw → warning + строка с `region = 'unknown'`.

**`core.calendar`** — зерно: день.
`date_day date PK`, `month_start date`, `year smallint`, `quarter smallint`, `month smallint`, `iso_week smallint`, `dow smallint`, `is_weekend bool`.
Диапазон **вычисляется** (не хардкод): от первой `purchase_date` до конца года последней даты среди моментов заказа (`purchase_ts`, `approved_ts`, `carrier_handoff_ts`, `delivered_ts`, `estimated_delivery_date`). Даты отзывов и `shipping_limit_ts` в расчёт не входят: на календарь они не ссылаются, а выбросы `shipping_limit` в 2020 году (1.3 п. 10) растянули бы календарь на два пустых года. Календарь нужен, чтобы пустые месяцы (2016-11) не пропадали из отчётов.

### 3.3 Сущности

**`core.customer`** — зерно: человек (`customer_unique_id`).
`customer_id uuid PK` (= unique_id). Других атрибутов в источнике нет: адрес хранится на заказе. Таблица нужна как точка FK и для будущих атрибутов (сегмент, дата регистрации).

**`core.seller`** — зерно: продавец.
`seller_id uuid PK`, `zip_prefix char(5)` (lpad, CHECK `~ '^\d{5}$'`), `city text` (как в источнике, lower/trim), `state_code char(2) FK`, `is_city_suspicious bool` (содержит `/`, `\`, цифры).

**`core.product`** — зерно: карточка товара (не привязана к продавцу).
`product_id uuid PK`, `category_id smallint NOT NULL FK`, `name_length smallint`, `description_length integer`, `photos_qty smallint`, `weight_g integer`, `length_cm`, `height_cm`, `width_cm smallint`, `volume_cm3 integer GENERATED ALWAYS AS (…) STORED`. Колонки называем `length`, а не `lenght`: опечатка остаётся только в raw. Вес 0 (4 товара) и NULL (2) — не исправляем, логируем.

### 3.4 Факты

**`core.customer_order`** — зерно: заказ.

| колонка | тип | источник / правило |
|---|---|---|
| order_id | uuid PK | |
| customer_id | uuid NOT NULL FK → customer | через raw.customers: `customer_id → customer_unique_id` |
| source_customer_id | uuid UNIQUE NOT NULL | исходный `customer_id` (ID покупателя-в-заказе), для трассировки |
| status_code | text NOT NULL FK → order_status | |
| purchase_ts | timestamp NOT NULL | |
| purchase_date | date NOT NULL FK → calendar | `purchase_ts::date`, для join с календарём и индексов |
| approved_ts | timestamp | NULL допустим |
| carrier_handoff_ts | timestamp | `order_delivered_carrier_date` |
| delivered_ts | timestamp | `order_delivered_customer_date` |
| estimated_delivery_date | date NOT NULL | |
| ship_zip_prefix | char(5) | адрес доставки — снимок на момент заказа |
| ship_city | text | |
| ship_state_code | char(2) FK → state | |

Никаких денежных агрегатов в `core.customer_order` нет: они выводятся из позиций и платежей, а дублирование сумм в core — источник расхождений, с которыми мы боремся. Агрегаты живут в `mart.order_summary`.

**`core.seller_shipment`** — зерно: часть заказа одного продавца (order × seller). Это «каждый продавец отгружает свою часть сам, у него крайний срок».
`order_id uuid`, `seller_id uuid`, PK (`order_id`, `seller_id`), FK на order и seller, `shipping_limit_ts timestamp NOT NULL`.
Сборка: `GROUP BY order_id, seller_id`. Инвариант «один срок на пару» проверяется самопроверкой (уровень error): если во «вбросе» он нарушится, сборка падает с понятным сообщением, а не берёт молча `max()`.
Ограничение источника (в записку): дата передачи перевозчику есть только на уровне заказа. Для 1 278 мультипродавцовых заказов «опоздание продавца» считается приближённо.

**`core.order_item`** — зерно: **одна единица товара в заказе** (атомарное зерно источника).
`order_id uuid`, `item_seq smallint` (= `order_item_id`), PK (`order_id`, `item_seq`), `product_id uuid FK`, `seller_id uuid`, FK (`order_id`, `seller_id`) → `seller_shipment`, `price numeric(12,2) NOT NULL CHECK (>= 0)`, `freight_amount numeric(12,2) NOT NULL CHECK (>= 0)`.
Почему не схлопываем в «строку с количеством»: сейчас дубли идентичны, но схлопывание теряет зерно и сломается, если у дублей появятся разные цены. Вместо этого — представление:

**`core.order_line` (VIEW)** — зерно: товар в заказе (order × product × seller), `quantity = count(*)`, `unit_price`, `goods_amount`, `freight_amount`. Отвечает на «сколько строк в заказе» (1.0385) в отличие от «сколько единиц» (1.1422).

**`core.payment`** — зерно: платёж заказа.
`order_id uuid FK`, `payment_seq smallint`, PK (`order_id`, `payment_seq`), `payment_type_code text FK`, `installments smallint CHECK (>= 0)`, `amount numeric(12,2) CHECK (>= 0)`.
Пропуски в seq и `installments = 0` не исправляем, логируем как warning.

**`core.review`** — зерно: отзыв.
`review_id uuid PK`, `score smallint NOT NULL CHECK (1..5)`, `title text`, `message text`, `created_ts timestamp`, `answered_ts timestamp`.
Дубли `review_id` в raw с идентичным содержимым схлопываются; с различающимся содержимым — error (сейчас 0 таких).

**`core.review_order`** — мост многие-ко-многим.
`review_id uuid FK`, `order_id uuid FK`, PK (`review_id`, `order_id`), вторичный индекс по `order_id`.

## 4. Схема `meta` (наблюдаемость сборки)

- **`meta.build_run`** — `run_id`, `started_at`, `finished_at`, `git_commit` (передаётся из build.sh через `psql -v`), `status`.
- **`meta.build_step`** — `run_id`, `step`, `rows_in`, `rows_out`, `duration_ms`.
- **`meta.rejected_row`** — `source_table`, `reason`, `raw_row jsonb` (`to_jsonb(r)`). Строки, которые нельзя загрузить: невалидный/NULL ключ, обязательное поле не приводится к типу, ссылка на отсутствующий заказ. Ссылка на отсутствующее измерение строку не отбраковывает — создаётся выведенный член (5.1).
- **`meta.dq_issue_type`** — справочник проблем: `issue_code PK`, `severity` (`error`/`warning`/`info`), `max_share numeric` (порог доли строк, NULL — без порога; 6.15), `description`.
- **`meta.dq_issue`** — построчный лог: `issue_code FK`, `entity`, `entity_key text`, `details jsonb`. Все пункты из 1.3 сюда (например `CARRIER_BEFORE_APPROVAL`, `DELIVERED_WITHOUT_DATE`, `ZIP_RESTORED_LEADING_ZERO`, `CATEGORY_UNKNOWN`, `PAYMENT_SEQ_GAP`, `SHIPPING_LIMIT_OUTLIER`, `REVIEW_BEFORE_PURCHASE`, `PAYMENT_ITEMS_MISMATCH`, `CAST_FAILED`…).
- **`meta.dataset_info`** — одна строка: `data_as_of`, границы данных и рабочего периода (5.1).
- **`meta.check_result`** — результаты самопроверок: `check_name`, `severity`, `expected`, `actual`, `passed`.

Принцип: **мы не чиним данные молча.** Правим только то, что однозначно (тип, ведущий ноль, пробелы), остальное оставляем как есть и помечаем. Аналитик сам решает, исключать ли помеченные строки.

## 5. Схема `mart`

**`mart.order_summary`** — **таблица** (не view), строится в конце сборки. Зерно: заказ. Рабочая лошадка для большинства вопросов и дашборда.
Колонки: всё из `core.customer_order` + `status.is_revenue`, `n_lines`, `n_units`, `n_sellers`, `goods_amount`, `freight_amount`, `order_total` (= goods + freight), `payment_total`, `n_payments`, `max_installments`, `payment_mismatch_amount`, `review_score` (правило при нескольких отзывах: **последний по `created_ts`, затем `answered_ts`** — зафиксировать в записке), `n_reviews`, `delivery_days`, `delay_days` (delivered − estimated), `is_late`, `is_first_order` (номер заказа покупателя через `row_number()` по `purchase_ts`), `customer_order_seq`, `has_items`, `has_payment`, `has_review`, `dq_flags text[]`, `has_dq_issue`, `observed_days`, `prev_order_gap_days` (дней с предыдущего заказа покупателя; 0 — одновременный заказ, раздел 1.3 п. 14). Правила для пустых и противоречивых значений — раздел 5.1.
Индексы: PK `order_id`; `(purchase_date)`; `(customer_id)`; частичный `WHERE is_revenue`.

**Представления ответов** `mart.q01_monthly_revenue` … `mart.q05_category_revenue`, позже `q06`–`q10`. Каждое читает только `core.*` / `mart.order_summary`, никогда `raw`.
- Q1: календарь LEFT JOIN, месяцы из `core.calendar` → 24 строки с нулём. Выводить две колонки: `orders_placed` и `orders_delivered` (контроль задаёт только выручку, определение «числа заказов» фиксируем явно).
- Q2: ID продавца через `core.fmt_id`.
- Q3: `avg_order_total`, `avg_lines` (через `order_line`), `avg_units`.
- Q4: основной ответ — по определению контроля (по заказам). Отдельной строкой — повторная покупка в другой день (`prev_order_gap_days > 0`), с пометкой, чем они отличаются.
- Q5: доля через `sum() over ()`; выводить и португальское, и английское название категории.

**`meta.metric`** — каталог показателей: `metric_code`, `name_ru`, `formula` (текст), `grain` (позиция / заказ / покупатель / продавец), `source_object`, `additivity` (`additive` / `semi_additive` / `non_additive`), `null_policy`, `used_in` (какие ответы). Заполняется для всех показателей ответов и `order_summary`. Это источник для концепции дашборда (критерий 5 прямо спрашивает про источник показателей и неаддитивные показатели) и для защиты. Структуру и технические поля заполняет агент, формулировки команда проверяет.

### 5.1 Неполные и противоречивые данные: как они попадают в показатели

Раздел 6.15 описывает данные, которые **нельзя прочитать** (мусор вместо даты). Здесь — данные, которые читаются, но **отсутствуют** или **противоречат друг другу**. Таких в выгрузке больше всего (раздел 1.3), и именно они дают «разные цифры у разных аналитиков».

Принцип: **данные в `core` не исправляем, а правило учёта задаём в определении показателя и делаем исключения видимыми.** Аналитик всегда может увидеть, сколько строк попало в расчёт и сколько выпало.

#### Отсутствующая связь (сирота)

| случай | политика | почему |
|---|---|---|
| факт ссылается на отсутствующее **измерение**: позиция → нет товара или продавца, заказ → нет покупателя | **выведенный член** (inferred member): создаётся строка измерения с этим ID и `is_inferred = true`, атрибуты пустые, категория — `unknown`; код `INFERRED_<сущность>` в `meta.dq_issue` | факт продажи достоверен; если его выбросить, потеряется выручка и разойдётся сверка денег |
| строка ссылается на отсутствующий **заказ**: позиция, платёж или отзыв без заказа | в `meta.rejected_row` | без заказа нет ни даты, ни статуса, ни покупателя — строку не к чему отнести |

Сейчас сирот нет, политика нужна на случай вброса. На выведенных членов действует тот же порог из 6.15: больше 1 % строк измерения → error. В `core.customer`, `core.seller`, `core.product` добавляется колонка `is_inferred bool NOT NULL DEFAULT false`. Для выведенного покупателя ключом служит исходный `customer_id`: настоящего `customer_unique_id` взять негде, и покупатель будет посчитан отдельным человеком, что видно по флагу.

#### Отсутствующие дочерние строки

- **Суммы по отсутствующим строкам = 0, а не `NULL`:** у заказа без позиций `goods_amount = 0`, `n_units = 0`; у заказа без платежей `payment_total = 0`. Сумма пустого множества — ноль; `NULL` в денежной колонке ломает сложение по срезам.
- **Факт наличия — отдельным флагом:** `has_items`, `has_payment`, `has_review` в `mart.order_summary`. Так «заказ на 0» отличается от «заказа без позиций».
- 775 заказов без позиций входят в `orders_placed`, но не в выручку и не в средний чек. Все они не `delivered`; самопроверка (warning) следит, чтобы среди `delivered` заказов без позиций не появилось.

#### Пустые значения в атрибутах

Общее правило: **значение `NULL` исключается и из числителя, и из знаменателя показателя, а рядом выводится покрытие** (сколько строк участвовало). Логические признаки трёхзначны: `NULL` означает «неизвестно», а не `false`.

| поле | сколько сейчас | влияние |
|---|---|---|
| `delivered_ts` у `delivered` | 8 | в выручку входят (правило по статусу); `delivery_days`, `delay_days`, `is_late` = `NULL`. Доля опозданий = `count(is_late) filter (true) / count(is_late)`, а не `/ count(*)` |
| `approved_ts` | 14 у delivered, 141 у canceled, 5 у created | показатели времени подтверждения считаются без них |
| `carrier_handoff_ts` | 2 у delivered + все недоставленные | соблюдение срока отгрузки продавцом = `NULL` |
| нет отзыва | 768 заказов | средняя оценка — по заказам с отзывом; рядом доля заказов с отзывом |
| категория | 610 товаров | категория `unknown` (раздел 3.2) — единственное место, где `NULL` заменяется явным значением, потому что категория — ключ среза |
| габариты, вес | 2 `NULL`, 4 веса = 0 | в показателях по весу и объёму вес 0 считается неизвестным (`nullif(weight_g, 0)`); в `core` хранится как есть |
| `installments` = 0 | 2 платежа | в показателях рассрочки — неизвестно |

#### Противоречивые значения

Строки сохраняются как есть, проблема фиксируется в `meta.dq_issue`, а коды проблем уровня заказа протягиваются в `mart.order_summary` колонками `dq_flags text[]` и `has_dq_issue bool`. По умолчанию показатели считаются **по всем** строкам, а флаги позволяют аналитику отфильтровать спорные.

Исключения из «по всем» — только там, где противоречие делает само значение бессмысленным:

- **Длительности.** `delivery_days`, `handoff_days` и т. п. считаются только при правильном порядке событий. Отрицательная длительность → `NULL` + флаг (23 вручения раньше передачи перевозчику, 166 передач раньше оформления). Исходные моменты времени в `core` не меняются.
- **Статус против дат.** Статус — источник истины о судьбе заказа. 6 `canceled` с датой вручения остаются отменёнными: не входят в выручку и в показатели доставки. Набор заказов для показателей доставки — `status = delivered`, `delivered_ts` заполнен, порядок событий корректный.
- **Платежи против позиций** (366 заказов): выручка считается по позициям (решение команды), платежи — отдельной суммой. В `order_summary` есть `payment_mismatch_amount`; две суммы никогда не подменяют друг друга.
- **`shipping_limit` в 2020 году** (4 позиции): остаётся как есть, флаг. На соблюдение срока не влияет: отгрузка всё равно раньше срока.

#### Неполные периоды

- **`meta.dataset_info`** (одна строка, вычисляется в сборке): `data_as_of` = последний момент любого события в данных (сейчас 2018-10-17 17:30:18 по заказам; ответы на отзывы — до 2018-10-29), первый и последний месяц с заказами, число заказов по месяцам.
- **`core.calendar`** получает `is_in_data_range` и `is_complete_month` (месяц закончился до `data_as_of`).
- **Хвост выгрузки:** в сентябре и октябре 2018 года 20 заказов и ни одного доставленного. Это не падение бизнеса, а конец выгрузки. Запуск площадки (сентябрь–декабрь 2016) тоже редкий: 329 заказов, в ноябре — ноль. Автоматически такие периоды надёжно не определить, поэтому границы «рабочего» периода (по умолчанию 2017-01 … 2018-08) — **решение команды**, записанное в `meta.dataset_info` и в записке, а не в каждом запросе. Отчёты за заданный в вопросе период (как Q1) показывают его целиком; тренды и дашборд помечают неполные и нетипичные месяцы.
- **Правое цензурирование.** Показатели, которым нужно время «созреть» (повторная покупка, доставка, отзыв), для последних когорт занижены: покупатель из августа 2018 просто не успел вернуться. В `order_summary` есть `observed_days = data_as_of − purchase_ts`. Сравнение когорт допустимо только при одинаковом окне наблюдения: например, «повторная покупка за 90 дней» только для когорт, у которых `observed_days ≥ 90`. Контроль Q4 считает без окна — это определение организаторов, и оно фиксируется в ответе.

6. **Стадии независимы и идемпотентны.** Каждую можно запустить отдельно, повтор ничего не ломает, тяжёлые стадии пропускаются, если вход не изменился.
7. **Падать громко и по месту:** у каждой стадии свой код выхода и сообщение «что сломалось и что делать», полный лог — в `logs/`.

### 6.2 Git

- Remote `origin` — наш форк, `upstream` — `daniilivanovp-droid/hackathon-students` (ветка `main`).
- Корень меняется **только** слиянием из upstream. Чужие именные папки не трогаем. Тогда `git merge upstream/main` всегда проходит без конфликтов: организаторы не знают о наших папках, а мы не трогаем их файлы.
- Ветки нашего решения — с префиксом: `inchanterx/<этап-или-задача>`. PR в `main` форка затрагивает только `inchanterx/` (и, один раз, `.github/workflows/inchanterx.yml`).
- `./run.sh sync` запускает **только человек**: слияние меняет файлы организаторов в корне, а агенту это делать запрещено (CLAUDE.md). Агент, увидев, что нужен `sync`, останавливается и просит.
- `./run.sh sync`: `git fetch upstream` → показать `git diff --stat HEAD upstream/main` и полный diff `docs/tasks.md` (там появятся вопросы 6–10 и вброс) → `git merge --ff-only upstream/main`, при невозможности — `git merge --no-edit`; при конфликте — стоп и сообщение. Делается на ветке `main` форка, затем `main` вливается в рабочую ветку.
- После `sync` пайплайн сам решает, нужна ли перезаливка `raw`: изменение `../scripts/` или данных меняет отпечаток (6.6).

### 6.3 Docker и база

**Контейнер** — сервис `postgres` из `../docker-compose.yml` организаторов, без изменений: `hack_postgres`, порт `5432`, `hack/hack`. Он общий для всех решений на машине.

**База данных — своя для каждого решения:** `SOLUTION_DB` (по умолчанию = имя папки, то есть `inchanterx`). База `marketplace` остаётся за организаторами и их `setup.sh`. Внутри нашей базы — стандартные схемы `raw`, `core`, `mart` (+ `meta`, `ops`), как требует задание. Это и есть изоляция: решения не перетирают друг другу `core`, вброс в одной базе не задевает другие, а `build.sql` работает в любой базе, в том числе в `marketplace` на чистой машине проверяющих.

**Вызов compose** из `run.sh` — всегда одной функцией:
```
docker compose --project-directory "$ROOT" \
  -f "$ROOT/docker-compose.yml" -f "$SOL_DIR/compose.pipeline.yml" …
```
Проект тот же, что у `setup.sh` организаторов (имя по папке корня), поэтому уже запущенный ими или коллегой контейнер переиспользуется, а не дублируется. Относительные пути в `compose.pipeline.yml` считаются от корня (`--project-directory`), поэтому в нём используется переменная `SOLUTION_DIR`, которую экспортирует `run.sh`.

**`compose.pipeline.yml`** добавляет один сервис и **не трогает `postgres`**. Любое изменение конфигурации их сервиса заставило бы compose пересоздать общий контейнер при каждом нашем `up` и выбило бы коллег. Тюнинг Postgres на 550 тыс. строк не нужен.

- **`pipeline`**, `profiles: ["pipeline"]` (сам по себе не стартует):
  - `build: ./${SOLUTION_DIR}/tools`, `image: capibara-pipeline-${SOLUTION}` (свой тег, чтобы образы разных решений не перетирали друг друга);
  - образ: `FROM postgres:16-alpine` (тот же, что у базы: слой уже скачан, `psql`/`pg_isready` версии 16) + `apk add bash curl python3 py3-psycopg2 coreutils`. `git` в образе не нужен: всё, что связано с git, `run.sh` делает на хосте (6.8);
  - `volumes: [".:/work"]` (весь корень: нужны `../scripts`, `../data`, `../docs`), `working_dir: /work/${SOLUTION_DIR}`;
  - `user: "${HOST_UID:-0}:${HOST_GID:-0}"`. На Linux `run.sh` экспортирует `HOST_UID=$(id -u)`, `HOST_GID=$(id -g)`, чтобы файлы в `../data`, `answers/`, `logs/` не стали принадлежать root. На Windows и macOS (Docker Desktop) владелец файлов на bind mount не важен, и переменные не экспортируются: `id -u` в Git Bash даёт uid MSYS (например 197609), которого в контейнере нет;
  - `environment`: `PGHOST=postgres PGPORT=5432 PGUSER=hack PGPASSWORD=hack PGDATABASE=${SOLUTION_DB} HOME=/tmp` (`HOME` — потому что у пользователя с uid хоста в образе нет домашней папки);
  - `depends_on: postgres: condition: service_healthy`.

**`.env.example`** (коммитим; `.env` — в `inchanterx/.gitignore`): `SOLUTION_DB=` (**пусто**: пустое значение = имя папки), `ANALYST_PASSWORD`, `UPSTREAM_URL`. `run.sh` читает `inchanterx/.env` сам и передаёт значения в compose через `--env-file`/экспорт: `.env` в корне не используем, он был бы общим для всех. Явное `SOLUTION_DB` в `.env` — только сознательная настройка человека.

Допущение: на одной машине — один клон форка. Два клона с разными именами папок дали бы два compose-проекта и конфликт имени контейнера `hack_postgres` (оно задано организаторами).

#### Хост на Windows (Git Bash + Docker Desktop)

Основная машина команды — Windows 11, Git Bash, Docker Desktop (WSL2). Что из этого следует:

- **Окончания строк.** При `core.autocrlf=true` (по умолчанию в Git for Windows) скрипты организаторов попадают на диск с CRLF, и `bash ../scripts/download_data.sh` в Linux-контейнере падает на `$'\r'`. Файлы организаторов не меняем и не обходим подменой. Решение — локальная настройка клона, которую `preflight` проверяет:
  ```
  git config core.autocrlf input
  rm scripts/*.sh scripts/load_raw.py scripts/init/*.sql && git checkout -- scripts
  ```
  (файлы организаторов у нас не меняются, поэтому повторная выгрузка ничего не теряет). Найден CR в `../scripts/*.sh` или `../scripts/*.py` → код 10 с этой инструкцией. Наши файлы защищены `inchanterx/.gitattributes` (`eol=lf`) независимо от настроек клона.
- **Пути.** Корень для `docker compose -f` берётся через `cygpath -m` на MSYS (`D:/repositories/...`), чтобы не зависеть от автоконвертации путей Git Bash.
- **uid** — см. `user:` выше.
- **`flock` в Git Bash нет** → блокировка запуска через атомарный `mkdir` (6.15).
- **Симлинки** в Git Bash по умолчанию создаются копией → `logs/latest.log` — копия последнего лога, а не симлинк (6.4).
- **TTY.** Интерактивный `./run.sh psql` в терминале VS Code (ConPTY) работает напрямую, в mintty нужен `winpty`; неинтерактивные стадии запускаются через `docker compose run -T`.
- **Ctrl+C** доходит до `docker.exe` и контейнера менее надёжно, чем в Linux (6.15, «Прерывание»).

### 6.4 Точка входа `run.sh`

Bash, `set -Eeuo pipefail`, `trap … ERR` печатает имя упавшей стадии и путь к логу. Весь вывод — через `tee` в `logs/run-<YYYYmmdd-HHMMSS>.log`; в конце запуска (и при ошибке) лог копируется в `logs/latest.log` (не симлинк — 6.3). Запускается из любого места: сам находит `SOL_DIR` (папку скрипта) и `ROOT`.

На хосте выполняются `preflight`, `sync`, `up`. Всё остальное — `docker compose run --rm pipeline ./run.sh --inside <stage>`: тот же скрипт перезапускает себя в контейнере. Один файл, без дублирования логики.

```
./run.sh                 = up → data → raw → build → test → answers   (полный прогон)
./run.sh --reset         то же, но сначала DROP DATABASE нашей базы (только нашей)
./run.sh <stage> [...]   только перечисленные стадии
./run.sh --force-raw     перезалить raw, даже если отпечаток не изменился
./run.sh status          контейнер, наша база, отпечаток raw, последний build_run, итоги проверок, блокирующие сессии
./run.sh psql            psql в нашу базу
./run.sh fault <name|all>  сценарий сбоя в одноразовой базе (6.15)
./run.sh bundle          собрать dist/build_all.sql (6.8)
```

**`--reset` никогда не делает `docker compose down -v`**: это удалило бы общий контейнер с базами коллег и `marketplace`. Сброс = `DROP DATABASE IF EXISTS "<SOLUTION_DB>" WITH (FORCE)` и полный прогон. Пересоздание всего контейнера — только `bash scripts/setup.sh --reset` организаторов и только по договорённости в команде.

`Makefile` — тонкая обёртка (`make all|up|data|raw|build|test|answers|sync|reset|psql|status`). Каноничен `run.sh`: на Windows/WSL make может не быть.

### 6.5 Стадии

| стадия | где | что делает | пропуск | код выхода при сбое |
|---|---|---|---|---|
| `preflight` | хост | есть docker, daemon жив, `docker compose` v2, git; найден корень с `docker-compose.yml` организаторов; в `../scripts` нет CRLF (6.3); имя папки допустимо (6.1 п. 5); создать `.env` из `.env.example`, если нет | — | 10 |
| `sync` | хост | раздел 6.2. **Не входит** в полный прогон: только явно | — | 15 |
| `up` | хост | `docker compose build pipeline` (кэшируется), `docker compose up -d --wait postgres` | контейнер уже healthy | 20 |
| `data` | pipeline | `bash ../scripts/download_data.sh` → `sha256sum -c data.sha256` (файлы в `../data`) | все хэши совпали | 30 |
| `raw` | pipeline | создать базу `SOLUTION_DB`, если её нет (подключение к служебной `postgres`, `CREATE DATABASE` через `\gexec`), `ALTER DATABASE … SET search_path TO core, public` → `python3 ../scripts/load_raw.py --host postgres --db $SOLUTION_DB` → применить `inject/*.sql` → сверить число строк с `data.rows` → записать отпечаток | отпечаток не изменился и `raw.orders` не пуст | 40 |
| `build` | pipeline | `psql -v ON_ERROR_STOP=1 -v git_commit=… -v raw_fingerprint=… -v analyst_password=… -f model/build.sql` (транзакция открывается внутри `build.sql`, 6.8) | — (всегда, секунды) | 50; 55 — упала самопроверка |
| `test` | pipeline | `psql -f tests/controls.sql`, табличка PASS/FAIL | — | 60 (сборка при этом остаётся) |
| `answers` | pipeline | выгрузка `mart.q*` в `answers/out/qNN.csv` + `answers/results.md` (`answers/export.py`: текст SQL view + таблица результата) | — | 70 |

Полный прогон выполняет стадии из списка, которые уже реализованы: на этапе A это `up → data → raw → build`, `test` добавляется на этапе B, `answers` — на этапе C. Нереализованная стадия, вызванная явно, — ошибка с подсказкой, а не тихий пропуск.

Полная таблица кодов выхода и правила, какие стадии выполняются после сбоя, — в разделе 6.15. Каждая стадия внутри `pipeline` начинается с короткого ожидания подключения (`pg_isready -h postgres`, до 60 с) — обычная практика для клиента базы в соседнем контейнере.

`load_raw.py` организаторов принимает `--db`, сам создаёт схемы `raw/core/mart` и таблицы `raw`, пути к CSV и DDL считает от своего расположения — его можно вызывать как есть. Его DDL делает `DROP TABLE raw.*` **без `CASCADE`**, поэтому ни один объект `core`/`mart`/`meta` не должен зависеть от таблиц `raw` (никаких view поверх `raw`): иначе перезаливка `raw` упадёт. Сборка читает `raw` только через `INSERT … SELECT`.

  Проверка — из `../data` (`cd ../data && sha256sum -c ../inchanterx/data.sha256`, путь вычисляется, а не хардкодится).
- **Хэши выше на этой машине ещё не подтверждены.** `download_data.sh` качает оригинальную выгрузку Olist с GitHub, а handout говорит, что идентификаторы «заменены на случайные строки». При первом скачивании хэши сверяются; если не совпали — стоп и сообщение команде, `data.sha256` автоматически не переписывается. Решение принять фактические файлы (`--accept-new`) принимает человек.
- Хэш не совпал → стадия останавливается и перечисляет отличающиеся файлы. `download_data.sh` пропускает любой непустой файл, поэтому недокачанный файл сам не исправится: сообщение подсказывает удалить его и повторить. Если организаторы **сознательно** подменили CSV во вбросе, `./run.sh data --accept-new` пересчитывает `data.sha256`, а после ближайшей загрузки `raw` — `data.rows`; оба изменения коммитятся отдельным коммитом, чтобы смена данных была видна в истории.
- **`data.rows`** — ожидаемое число строк каждой таблицы `raw` (сейчас — раздел 1.1, всего 550 759). Это свойство версии данных, а не модели, поэтому живёт рядом с `data.sha256`, а не в `run.sh` и не в `model/`.
- **Отпечаток raw** = sha256 от `data.sha256` + `../scripts/load_raw.py` + `../scripts/init/*.sql` + `inject/*.sql`. Хранится в `ops.raw_state` нашей базы (`fingerprint`, `loaded_at`, `row_counts jsonb`). Схему `ops` не трогает ни сборка (`core/mart/meta` пересоздаются), ни загрузчик (он пересоздаёт только таблицы `raw`). Совпал отпечаток и `raw.orders` не пуст → стадия `raw` пропускается, повторный `./run.sh` занимает секунды.
- После загрузки и патчей `inject/` — сверка строк `raw` с `data.rows`. Расхождение при совпавших хэшах и пустом `inject/` → ошибка (код 40): загрузчик прочитал файлы не так, как раньше. Если расхождение объясняется `inject/` или `--accept-new` → warning, новые цифры пишутся в `ops.raw_state`, а при `--accept-new` — и в `data.rows`.

### 6.7 Вброс: куда класть и как прогонять

Формат вброса заранее неизвестен, поэтому три пути:

- **Новые вопросы** (`../docs/tasks.md`) → `./run.sh sync` → дописать `mart.q06…q10` → `./run.sh build test answers`.
- **Изменённые/новые CSV или скрипты организаторов** → `sync` (или файл руками в `../data` + `data --accept-new`) → отпечаток изменился → `raw` перезальётся сам → `build`. Данные в `../data` общие: если коллега принял новые CSV, наша стадия `data` это заметит по хэшам.
- **SQL-патч к raw** (например «добавьте эти строки») → `inject/NN_<описание>.sql`; стадия `raw` применяет их по порядку **после** загрузчика, только к нашей базе, и включает в отпечаток. `load_raw.py` при каждом запуске делает TRUNCATE, поэтому патч, применённый руками в `psql`, исчез бы при следующей перезаливке; через `inject/` он воспроизводим.

`inject/` — единственное место, где наше решение может менять `raw`, и только потому, что так велят организаторы. Каждый файл — с комментарием-ссылкой на условие вброса.

### 6.8 Стадия `build` изнутри

- `model/build.sql` — мастер-файл с `\ir` остальных по порядку (6.1). Сборка работает в текущей базе и не содержит её имени.
- **Сборка запускается и без нашего пайплайна.** Сдаётся «SQL-скрипт, который собирает модель из `raw` с нуля», и проверяющие могут запустить его сами на базе `marketplace`, загруженной их `setup.sh`. Поэтому:
  - `build.sql` сам открывает и закрывает транзакцию (`BEGIN` … `COMMIT`), а `run.sh` не передаёт `--single-transaction` (иначе транзакции вложились бы);
  - `psql`-переменные (`git_commit`, `raw_fingerprint`, `analyst_password`) необязательны: в `build.sql` значения по умолчанию через `\if :{?git_commit} … \else \set git_commit 'unknown' \endif`. Внутрь номерных файлов переменные не передаются: мастер кладёт их в настройки сессии (`SELECT set_config('capibara.git_commit', :'git_commit', true)`), а файлы читают их через `current_setting('capibara.git_commit', true)`. В номерных файлах нет ни одной psql-команды;
  - без `analyst_password` роль не создаётся (сообщение `NOTICE`), сборка проходит;
  - `ops` создаётся через `CREATE SCHEMA IF NOT EXISTS`, сборка не зависит от того, запускался ли пайплайн;
  - достаточно команды `psql -v ON_ERROR_STOP=1 -d marketplace -f inchanterx/model/build.sql`.
- **Однофайловая сборка для GUI-клиентов.** DBeaver и pgAdmin не понимают `\ir` и `\if`. `./run.sh bundle` склеивает номерные файлы в `dist/build_all.sql`: чистый SQL в одной транзакции, значения переменных по умолчанию, без создания роли. Файл коммитится. CI проверяет, что `build_all.sql` актуален и собирает ту же модель.
- В начале `build.sql`: `pg_try_advisory_xact_lock` (6.15), `SET lock_timeout = '10s'`, `SET statement_timeout = '5min'`, `SET client_min_messages = warning`. `DROP SCHEMA core CASCADE` берёт эксклюзивную блокировку; если у кого-то в DBeaver висит долгий запрос или незакрытая транзакция к нашей базе, сборка без таймаута молча зависнет. С таймаутом она падает с кодом 50 и подсказкой (`./run.sh status` покажет блокирующие сессии через `pg_stat_activity` / `pg_blocking_pids`).
- Пока идёт сборка, читатели старой версии ждут коммита и не видят полусобранную модель.
- `meta.build_run` получает `git_commit` (`git rev-parse --short HEAD` + `-dirty`, если в `inchanterx/` есть незакоммиченные изменения) и `raw_fingerprint`. Любая цифра в ответах прослеживается до коммита кода и версии данных. `git_commit` вычисляет `run.sh` **на хосте** и передаёт в контейнер переменной окружения: git внутри контейнера споткнулся бы о `safe.directory` (другой владелец репозитория) и на Windows видел бы все файлы изменёнными из-за CRLF.
- Порядок внутри: таблицы без индексов → `INSERT … SELECT` → PK/FK/CHECK/индексы → DQ → mart → комментарии → самопроверки → `ANALYZE` → роли и гранты.
- Дедупликация: точные дубли по ключу схлопываются через `DISTINCT ON (key) … ORDER BY key, <полный порядок до уникальности, 3.1>`; дубли ключа с разным содержимым — в `meta.dq_issue` (error или warning — по таблице).
- Отбраковка и выведенные члены — по политике раздела 5.1: строки без заказа-родителя и с непригодными обязательными полями → `meta.rejected_row`; ссылки на отсутствующие товар, продавца или покупателя → выведенный член с `is_inferred = true`.
- Никаких захардкоженных контрольных цифр в сборке: после вброса цифры законно изменятся.

### 6.9 Доступ к базе

- Контейнер и учётка — организаторов, база — наша: `postgresql://hack:hack@localhost:5432/inchanterx`.
- **Для команды** — одна машина-хост (ноутбук или VPS), с которой все работают: через Tailscale (`…@<tailscale-ip>:5432/inchanterx`) или `ssh -L 5432:localhost:5432 user@host`. На такой машине решения всех участников живут рядом как отдельные базы одного контейнера — их удобно сравнивать между собой. Если у каждого своя копия, цифры в обсуждении сверяются по `meta.build_run.git_commit`.
- **Роль `<SOLUTION_DB>_analyst`** (роли в Postgres общие на весь кластер, поэтому имя с префиксом решения — иначе два решения перетирали бы пароль одной роли). Создаётся в `99_finalize.sql` идемпотентно (`DO`-блок с проверкой `pg_roles`), пароль из `-v analyst_password`: `LOGIN`, `CONNECT` только на нашу базу, `USAGE` + `SELECT` на `core`, `mart`, `meta`, никаких прав на `raw` и `ops`, `ALTER ROLE … SET default_transaction_read_only = on`. Гранты выдаются **в каждой сборке**: `DROP SCHEMA … CASCADE` их уничтожает.
- `./run.sh psql` → `psql` в нашу базу. pgAdmin организаторов доступен через их профиль `tools` (в нём нужно выбрать базу `inchanterx`).

### 6.10 Самопроверки (`90_checks.sql`)

Error — сборка падает (код 55), вся транзакция откатывается, старая версия модели остаётся:
1. **Сверка строк** по каждой raw-таблице: `raw = core + rejected + схлопнутые дубли`. Ответ на вопрос защиты «как убедились, что ничего не потеряли».
2. **Сверка денег:** `sum(price)`, `sum(freight)`, `sum(payment_value)` из raw (по валидным строкам) = из core, до копейки.
3. Каждый товар имеет категорию; сумма выручки по категориям = общая выручка.
4. Инвариант одного `shipping_limit` на (order, seller).
5. Каждый `review_id` с одинаковым содержимым во всех копиях.
6. Каждый заказ ссылается на существующего покупателя, статус и дату календаря.

Warning — пишется в `meta.check_result`, сборка идёт дальше:
- неизвестные статусы / типы платежей / штаты;
- пропуски в `item_seq` / `payment_seq`;
- аномалии хронологии (с количеством);
- расхождение платежей и позиций (число заказов, сумма).

В конце сборки — сводка в лог: строки по таблицам, число issue по кодам, предупреждения, время каждой стадии из `meta.build_step`.

### 6.11 `tests/controls.sql`

Запросы к `mart.q0X`, сравнение с контролем из `../docs/tasks.md`, вывод PASS/FAIL и итоговый `RAISE EXCEPTION`, если есть FAIL (код 60). Запускается отдельно от сборки: после вброса контрольные цифры могут законно разойтись, а модель при этом должна собираться.

### 6.15 Обработка ошибок

Принцип: каждая ошибка относится к заранее известному классу, и для каждого класса заранее решено, что делать: **остановиться**, **продолжить с записью в лог** или **повторить**. Молча проглоченных ошибок не бывает: `|| true`, `EXCEPTION WHEN OTHERS THEN NULL` и пустые `except` запрещены.

| целостность входа | хэш CSV не совпал с `data.sha256`; загрузчик организаторов упал на битом CSV | стоп, список файлов / сообщение загрузчика. Загрузчик не правим | 30, 40 |

#### Пороги для данных

Построчная обработка без порогов опасна: если вброс превратит половину дат в мусор, сборка «успешно» пройдёт с пустыми полями. Поэтому у каждого кода в `meta.dq_issue_type` есть политика:

- `severity` — `error` / `warning` / `info`;
- `max_share` — допустимая доля строк таблицы; превышение превращает warning в error.

Политика по умолчанию:
- **обязательное** поле (ключи, `purchase_ts`, `price`, `freight_value`, `payment_value`, `review_score`) не приводится к типу → строка целиком уходит в `meta.rejected_row`: заказ без даты оформления или позиция без цены в модели существовать не могут. Зависимые строки (позиции отбракованного заказа) отбраковываются следом как сироты, и сверка строк это учитывает;
- **необязательное** поле не приводится → `NULL` + `CAST_FAILED`, warning; свыше 1 % строк таблицы → error;
- отбракованных строк больше 1 % таблицы → error.

Пороги — это сиды `meta.dq_issue_type` в `model/10_meta.sql`, а не константы внутри проверок. Ослаблять порог, чтобы сборка прошла, без решения команды нельзя.

#### Атомарность и состояние между стадиями

- **`raw`.** Загрузчик организаторов работает одной транзакцией. Патчи `inject/` и запись отпечатка в `ops.raw_state` выполняются **одной транзакцией после него, отпечаток — последним**. Если патч упал, отпечаток не обновится, и следующий запуск перезальёт `raw` заново. Состояние «загружено, но не пропатчено» никогда не будет принято за готовое.
- **`build`.** Одна транзакция. При любой ошибке остаётся предыдущая успешная версия модели целиком.
- **Связь стадий.** В полном прогоне после упавшей `build` стадии `test` и `answers` не запускаются: они выгрузили бы цифры старой модели, собранной на другом `raw`. Если упала `test`, `answers` всё равно выполняется (после вброса контроль может законно не сойтись), но итоговый код выхода — 60.
- **Устаревшая модель.** `status` сравнивает `ops.raw_state.fingerprint` с `raw_fingerprint` последней успешной сборки и громко пишет, если `core` собран на старом `raw`. Отдельный запуск `test` или `answers` в таком состоянии отказывается работать (код 65) без флага `--allow-stale`.
- **Выходные файлы** (`answers/out/`, `answers/results.md`, `data.sha256` при `--accept-new`) пишутся во временный файл и переносятся через `mv`. Оборванный запуск не оставляет полуфайлов.

#### Журнал сборок, переживающий откат

Упавшая сборка откатывает и свою запись в `meta.build_run`, так что внутри транзакции след ошибки не сохранить. Поэтому:

- `ops.build_history` (схема `ops` переживает пересборку): `run_id`, `started_at`, `finished_at`, `status` (`success` / `failed` / `interrupted`), `exit_code`, `stage`, `git_commit`, `raw_fingerprint`, `error_text` (последние ~50 строк stderr), `row_counts jsonb`, `dq_counts jsonb`;
- запись делает `run.sh` **отдельным коротким вызовом psql после** основной стадии, и при успехе, и при ошибке. При успехе `row_counts` и `dq_counts` берутся из только что закоммиченной `meta`.

#### Самопроверки: все сразу и с деталями

- `90_checks.sql` не останавливается на первой упавшей проверке. Он прогоняет все, складывает результаты во временную таблицу и, если есть хотя бы один error, бросает **одно** исключение со списком всех упавших проверок.
- Формат: `RAISE EXCEPTION 'CHECK FAILED: …' USING DETAIL = '<проверка: ожидалось X, получено Y; …>', HINT = '<где смотреть>'`. Префикс `CHECK FAILED:` позволяет `run.sh` отличить упавшую самопроверку (код 55) от ошибки в коде (код 50).
- Все сообщения — на русском, по схеме «что случилось / где / что делать».

#### Отличие от прошлой сборки — детектор вброса

После каждой успешной сборки сводка сравнивает `dq_counts` и `row_counts` с последней успешной записью в `ops.build_history`. В конце лога выводится таблица изменений: новые коды проблем, коды с изменившимся количеством, таблицы с изменившимся числом строк. Это самый быстрый ответ на вопрос «что изменил вброс» и готовый материал для защиты.

#### Конкурентные запуски

- Локально: `run.sh` атомарно создаёт каталог `inchanterx/.run.lock/` (`mkdir` атомарен везде, `flock` в Git Bash нет) и пишет в него PID и время. Второй запуск на той же машине (агент + человек) сразу получает код 25: «уже идёт запуск, PID …». Блокировка снимается в `trap EXIT`; если процесс с записанным PID уже не существует (запуск убит), блокировка считается брошенной и перехватывается с предупреждением.
- В базе: первая команда `build.sql` — `pg_try_advisory_xact_lock(hashtext(current_database()))`. При неудаче — исключение «в этой базе уже идёт сборка». Защищает общую базу от запусков с разных машин.
- `run.sh` выставляет `PGAPPNAME=run.sh:<stage>:<user>@<host>`. `status` показывает активные сессии нашей базы и блокировки (`pg_stat_activity`, `pg_blocking_pids`), а сообщение при `lock_timeout` подсказывает, кто держит блокировку.

#### Прерывание

`trap INT TERM` печатает «прервано на стадии X», пишет `interrupted` в `ops.build_history` (если база доступна) и выходит с кодом 130. Сигнал доходит до psql в контейнере, запрос отменяется, транзакция откатывается на сервере. `docker compose run --rm` не оставляет контейнеров; `status` всё равно показывает оставшиеся `*-run-*` контейнеры нашего образа, если они есть.

На Windows-хосте Ctrl+C из Git Bash может убить `docker.exe`, не доставив сигнал в контейнер; тогда psql внутри продолжит работу и может закоммитить сборку, хотя хост уже считает её прерванной. Полусобранной модели не будет (сборка — одна транзакция), но журнал соврёт. Поэтому `trap` на хосте после прерывания явно останавливает контейнер стадии (`docker stop` по имени `*-run-*` нашего проекта) и только потом пишет `interrupted`. Поведение на Windows проверяется отдельно и записывается в `docs/AI_LOG.md` как есть.

#### Коды psql

psql с `ON_ERROR_STOP` возвращает: 0 — успех, 1 — фатальная ошибка самого psql (например, нет файла), 2 — потеряно соединение, 3 — ошибка в скрипте. `run.sh` переводит их в коды стадий: 2 → «соединение с базой потеряно» (код 20 и подсказка проверить контейнер), 3 → 50 или 55 по префиксу `CHECK FAILED:`, 1 → 50.

#### Сценарии сбоев как тесты

`tests/faults/` — набор SQL-сценариев, имитирующих вброс:
- дубль строк в `raw.order_items`;
- мусор в датах 10 % заказов;
- новый статус;
- позиция с несуществующим товаром;
- конфликтующие дубли отзыва;
- два разных `shipping_limit` у одной пары.

У каждого сценария в заголовке указаны ожидаемый код выхода и ожидаемые коды `dq_issue`.

`./run.sh fault <name>` прогоняет полный пайплайн в **отдельной одноразовой базе** `<SOLUTION_DB>_fault` с этим сценарием как дополнительным `inject` и сверяет результат с ожиданием. `./run.sh fault all` прогоняет все. Наша база не затрагивается, одноразовая удаляется после прогона. Это проверяет обработку ошибок до того, как настоящий вброс сделает это на защите.

## 7. Производительность

Объём (~550 тыс. строк) Postgres переваривает за миллисекунды. Наша задача — не «ускорить», а **не создать проблем и показать, что понимаем, где они появятся** (это в `docs/strategy.md`).

- `uuid` вместо text для ключей: индексы примерно вдвое меньше, сравнение — 16 байт.
- Узкие типы (`smallint`, `char(2)`, `date`), колонки фиксированной длины в начале таблицы (выравнивание кортежа).
- Индексы на все FK-колонки дочерних таблиц: `order_item(product_id)`, `order_item(seller_id)`, `customer_order(customer_id)`, `customer_order(purchase_date)`, `review_order(order_id)`. PK с ведущим `order_id` покрывает выборки позиций и платежей по заказу.
- `mart.order_summary` материализован: большинство вопросов — один проход по 99 тыс. строк без JOIN.
- `ANALYZE` в конце сборки, иначе планировщик работает вслепую на свежих таблицах.
- Проверка: `EXPLAIN (ANALYZE, BUFFERS)` для каждого q-запроса, сохранить в `answers/explain/`. Пригодится на защите.
- Партиционирование, BRIN по дате, колоночные хранилища — **не** делаем сейчас, описываем в стратегии с порогами.

## 8. Готовность ко второй половине и «вбросу»

Вероятные новые вопросы и откуда они считаются:

| тема | источник |
|---|---|
| опоздания доставки по штатам/регионам | order_summary.delay_days, ship_state → state.region |
| нарушение срока отгрузки продавцом | seller_shipment.shipping_limit_ts vs order.carrier_handoff_ts |
| оценка отзыва vs задержка | order_summary.review_score, is_late |
| структура оплат, рассрочка | payment, payment_type |
| доля доставки в чеке, по регионам | order_summary.freight_amount / order_total |
| когорты, удержание | order_summary.customer_order_seq, calendar.month_start |
| отмены, недоступность | order_status.is_cancelled, заказы без позиций |
| межрегиональные продажи | seller.state_code vs customer_order.ship_state_code |

Вероятные «вбросы» и реакция модели:
- новые дубли строк → дедупликация + сверка строк покажет сколько;
- новый статус / категория / тип платежа → автодобавление в справочник с `is_known=false` + warning;
- мусор в датах/суммах → `pg_input_is_valid` → NULL + `CAST_FAILED` в логе, сборка не падает;
- позиция с несуществующим товаром → выведенный член `core.product` (`is_inferred = true`, категория `unknown`) + `INFERRED_PRODUCT` в `meta.dq_issue`, позиция и её выручка сохраняются (5.1); позиция с несуществующим **заказом** → `meta.rejected_row`; сверка строк сходится в обоих случаях;
- изменение определения выручки (например «с доставкой») → правка в одном месте (`order_status.is_revenue` или одна колонка в order_summary).

## 9. Порядок работ для Claude Code

### 9.0 Приоритеты

План рассчитан на полный объём. Если времени не хватает, режется снизу вверх. Модель (30 баллов), ответы (30) и тексты команды (записка, дашборд, стратегия — 40) важнее обвязки, которая влияет в основном на «поддерживаемость» (15).

| приоритет | что входит | к какому моменту |
|---|---|---|
| **обязательно** | `core` целиком, `build.sql` с запуском без пайплайна, самопроверки строк и денег, `order_summary`, q01–q05 с PASS, `meta.dq_issue`, минимальный `run.sh` (`preflight`, `up`, `data`, `raw` с отпечатком и `inject/`, `build`, `test`, `psql`, `--reset`) | к чекпоинту с первыми ответами |

Отпечаток `raw` перенесён в «обязательно»: без него патчи `inject/` нельзя применить атомарно (6.15), а стоит он несколько строк. Этап A поэтому делится на A1 (обязательное, сразу), A2 (желательное, после обязательной части этапа B) и A3 (вместе с остальным «если останется время»).

Параллельные решения в именных папках — тоже расход времени. Команде стоит заранее назначить момент, когда выбирается одно решение для сдачи: на защите его должен уметь объяснить каждый.


**Этап A — окружение (раздел 6):**

- не обращаться к `raw` из `mart`; не создавать никаких объектов (view, FK), зависящих от таблиц `raw` (6.5);
