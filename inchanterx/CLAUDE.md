# CLAUDE.md — правила работы в репозитории

Этот файл действует в каждой сессии. Полная спецификация — в `PLAN.md`: прочитай его целиком перед первой задачей, дальше — нужные разделы перед каждым этапом.

## Проект

Хакатон, кейс «Модель маркетплейса Capibara». Строим модель данных в PostgreSQL 16: `raw` (дано организаторами) → `core` (наша модель) → `mart` (сводная таблица и ответы на вопросы). Интерфейс не делаем.

- Условие и описание данных: `../docs/handout.md`.
- Вопросы к модели: `../docs/tasks.md`. В середине хакатона организаторы допишут туда вопросы 6–10 и «вброс».
- Спецификация модели, пайплайна и порядок работ: `PLAN.md`.

## Где ты находишься

Репозиторий — форк организаторов (`origin` — наш форк, `upstream` — их репозиторий).

- **Корень форка — оригинальный репозиторий организаторов**: `docker-compose.yml`, `scripts/`, `docs/`, `data/`.
- **Наше решение — папка `inchanterx/`**, этот файл лежит в ней. Все пути в этом файле и в `PLAN.md` даны относительно `inchanterx/`; файлы организаторов — через `../`.
- **Другие участники команды делают альтернативные решения в своих именных папках** рядом с нашей. Это не наш код: не читай его как образец, не меняй, не ссылайся на него.
- Контейнер Postgres (`hack_postgres`, порт 5432) — общий для всех решений на машине. У каждого решения своя база данных: у нас — `inchanterx`. База `marketplace` принадлежит организаторам.

Структура папки и устройство пайплайна — `PLAN.md`, раздел 6.

## Команды

Создаются на этапе A (`PLAN.md`, раздел 6). Запускаются из `inchanterx/`.

```
./run.sh                    полный прогон: up → data → raw → build → test → answers
./run.sh --reset            то же с чистой базы (DROP DATABASE inchanterx, только нашей)
./run.sh build test         пересобрать модель и сверить контрольные цифры
./run.sh answers            выгрузить ответы в answers/
./run.sh psql               консоль нашей базы
./run.sh status             состояние окружения, последняя сборка, итоги проверок
./run.sh sync               подтянуть изменения организаторов
./run.sh fault <name|all>   сценарий сбоя в одноразовой базе
```

## Запреты

- Не менять ничего вне `inchanterx/`: ни файлы организаторов в корне (`docker-compose.yml`, `scripts/`, `docs/`), ни папки других участников. Единственное исключение — наш workflow CI `.github/workflows/inchanterx.yml`.
- Не переопределять сервис `postgres` организаторов и не выполнять `docker compose down -v`: контейнер общий, в нём базы коллег. Сброс — только `./run.sh --reset` (удаляет лишь нашу базу).
- Не трогать чужие базы данных и `marketplace`; не создавать роли без префикса `inchanterx_` (роли в Postgres общие на весь кластер).
- Не хардкодить имя `inchanterx` в коде: имя решения и базы вычисляется из имени папки / `.env`.
- Не менять данные в `raw`. Единственное исключение — SQL-патчи из условий вброса в `inject/`, и только по указанию команды.
- Объекты в `mart` читают только `core` (и `mart`). Обращение к `raw` из `mart` или из ответов запрещено, даже если цифра сойдётся.
- Не хардкодить контрольные цифры в сборке (`model/`). Им место только в `tests/controls.sql`.
- Не исправлять данные молча. Допустима только однозначная нормализация (типы, пробелы, ведущий ноль индекса); всё остальное остаётся как есть и помечается в `meta.dq_issue`.
- Не писать содержательный текст в `docs/decisions.md`, `docs/dashboard.md`, `docs/strategy.md` (внутри `inchanterx/`). Там можно создать только структуру разделов с `TODO`. Текст пишет команда, и он оценивается как её собственная работа. По запросу можно подготовить факты и цифры из базы для этих текстов.

## Соглашения

- Слои: `raw` → `core` → `mart`; служебные `meta` (журнал сборки, качество данных, самопроверки) и `ops` (состояние пайплайна). Все — в базе `inchanterx`; `model/build.sql` работает в текущей базе и её имени не содержит.
- Таблица заказов — `core.customer_order`. Ключ — `order_id`.
- Именование: snake_case, таблицы в единственном числе, `_ts` — timestamp, `_date` — date, `_amount` — деньги, `is_` / `has_` — boolean.
- Типы: ID источника → `uuid`; деньги → `numeric(12,2)`, никогда float; счётчики и габариты → `smallint` / `integer`.
- Приведение типов — через `pg_input_is_valid()`. Неудачное приведение даёт `NULL` + запись `CAST_FAILED` в `meta.dq_issue`; сборка из-за мусора в данных не падает.
- Сборка — одна транзакция, которую открывает и закрывает сам `model/build.sql`. Он обязан работать и без пайплайна: `psql -v ON_ERROR_STOP=1 -d marketplace -f model/build.sql`. psql-команды — только в `build.sql`; в номерных файлах — чистый SQL (PLAN 6.8). Индексы и ограничения создаются после наполнения, в конце — `ANALYZE`.
- ID в ответах и выгрузках — без дефисов, через `core.fmt_id()`. Округление — только в представлениях ответов.
- Детерминизм: у каждой оконной функции, `DISTINCT ON` и выгрузки — полный порядок до уникального ключа.
- Справочные данные, которые ты вписываешь из своих знаний (штаты, регионы, описания), помечай `source = 'manual'` и отмечай в `AI_LOG.md` как требующие проверки.
- Каждая таблица и каждая неочевидная колонка получают `COMMENT ON`: зерно, источник, правило.
- Комментарии в коде, сообщения скриптов и документы — на русском. Идентификаторы — на английском.

## Обработка ошибок

Политика — `PLAN.md`, раздел 6.15 (нечитаемые данные и сбои) и раздел 5.1 (неполные и противоречивые данные). Коротко:

- Каждая ошибка относится к классу из таблицы 6.15, и реакция на неё задана там: стоп, лог или повтор. Не придумывай реакцию по месту.
- Никогда не глуши ошибки: никаких `|| true`, `EXCEPTION WHEN OTHERS THEN NULL`, пустых `except`, `2>/dev/null` на значимых командах.
- Плохие строки данных не роняют сборку: они уходят в `meta.rejected_row` или в `NULL` + `meta.dq_issue`. Но пороги из `meta.dq_issue_type` превращают массовую порчу в error. Не ослабляй порог, чтобы сборка прошла.
- Сообщения об ошибках — на русском, по схеме «что случилось / где / что делать». Упавшие самопроверки — одним исключением с префиксом `CHECK FAILED:` и списком всех проверок.
- Коды выхода стадий — из таблицы 6.15, не выдумывай новые.
- Любое изменение в обработке ошибок сопровождается сценарием в `tests/faults/`.

## Решения команды

Эти решения принимает команда. Не меняй их и не «улучшай» по ходу работы. Если считаешь, что какое-то из них неверно, остановись и опиши проблему.

| решение | что выбрано |
|---|---|
| выручка | `sum(price)` **без доставки** по позициям заказов со статусом `delivered`; признак — `core.order_status.is_revenue`, правило живёт только там |
| средний чек | `price + freight` на заказ, только `delivered` |
| месяц заказа | месяц `purchase_ts` (оформления), не доставки |
| число заказов в Q1 | выводим две колонки: `orders_placed` и `orders_delivered` |
| покупатель | `customer_unique_id`; считаются заказы **всех** статусов |
| адрес | свойство заказа (снимок на `customer_order`), а не покупателя |
| зерно позиций | `core.order_item` = одна единица товара, без схлопывания; количество — через view `core.order_line` |
| срок отгрузки | в `core.seller_shipment` (заказ × продавец), не на позиции |
| несколько отзывов у заказа | берётся последний по `created_ts`, затем `answered_ts` |
| категории | явная категория `unknown` для пустых; непереведённые получают `name_en = name_pt` |
| ключи | натуральные ключи источника как `uuid`; суррогатные — только у справочников |
| повторная покупка (Q4) | основной ответ — по определению контроля; отдельно — повторная покупка в другой день |
| сирота факт → измерение | выведенный член (`is_inferred = true`), факт сохраняется |
| сирота без заказа-родителя | в `meta.rejected_row` |
| пустые значения в показателях | исключаются из числителя и знаменателя, рядом — покрытие; логические признаки `NULL` = «неизвестно» |
| суммы по отсутствующим строкам | 0, наличие — флагами `has_items` / `has_payment` / `has_review` |
| противоречия в данных | `core` не исправляем; флаги в `order_summary`; длительности при неверном порядке событий = `NULL` |
| рабочий период для трендов | 2017-01 … 2018-08; сентябрь–октябрь 2018 — хвост выгрузки (`meta.dataset_info`) |

- `order_line` (заказ × товар) — 102 425 строк;
- заказов без позиций — 775, без платежей — 1, без отзыва — 768.

## Порядок работы

- Работа идёт по этапам A → B → C из `PLAN.md`, раздел 9, с учётом приоритетов из 9.0: сначала всё «обязательное». Один этап — одна ветка с префиксом `inchanterx/` и один PR, затрагивающий только `inchanterx/`.
- Перед началом этапа покажи план: какие файлы создашь, в каком порядке, как проверишь. Начинай после подтверждения.
- Не переходи к следующему этапу, пока команда явно не подтвердила текущий.
- Коммиты маленькие, по одному логическому шагу. В сообщении — что сделано и зачем.

## Когда остановиться и спросить

- Решение из таблицы «Решения команды» кажется неверным.
- Цифра не сходится с приёмочной, и причина не очевидна.
- Задача требует изменить файлы организаторов или данные в `raw`.
- В данных найдено то, чего нет в `PLAN.md`, раздел 1.3.
- Требование из `PLAN.md` противоречит условию в `../docs/`.
- Для задачи, похоже, нужно изменить что-то вне `inchanterx/`.

## Готово, когда

Этап или задача считаются выполненными, только если:

1. `./run.sh --reset` проходит с нуля на чистой базе и не задевает `marketplace` и чужие базы.
2. Повторный `./run.sh` даёт тот же результат.
3. Самопроверки `90_checks.sql` проходят. Начиная с этапа B — и `./run.sh test` (все контроли PASS), и `./run.sh fault all`.
4. Нетривиальные правила описаны в `COMMENT ON`.
5. Сделана запись в `docs/AI_LOG.md`.
6. В описании PR: что сделано, **реальный вывод** проверочных команд, что осталось не сделанным или требует внимания человека.

## Журнал использования ИИ: `docs/AI_LOG.md`

Использование ИИ оценивается отдельно: прозрачность, проверка результата, собственные решения команды. После каждой завершённой задачи добавляй запись:

```
## <дата> — <этап / задача>
Сгенерировано: <файлы, объекты БД>
Решения агента: <технические мелочи, которые выбрал сам, и почему>
Проверено: <команда> → <фактический результат>
Требует проверки человеком: <что именно и почему>
```

Пиши «проверено» только про то, что действительно запускал. Если проверка не выполнялась, так и пиши.
