# Личная модель `core`: рабочие заметки

## Входной запрос

Формулировки пользователя в этой беседе:

> Давай подготовим нужные документы для разработки своей модели `core`
> Нас 5 участников. Наш план - подготовить несколько решений, потом прийти к консенсусу

Позднейшие уточнения:

> мы работаем по-одиночке. мы представляем индивидуальное решение

> также добавь в документацию свои размышления, входной промпт

> размышления и промпт нужны для того, чтобы в последствии, при объединении решений, можно было понять, откуда пришло то или иное решение

Каждый согласованный выбор и его происхождение записываются отдельно в [журнале решений](decision-log.md). Будущие варианты схемы должны ссылаться на соответствующие записи журнала.

## Согласовано

Актуальные решения и основания для каждого из них — в [журнале решений](decision-log.md). Пока это правила для личного проекта, а не итоговое решение команды.

## Моя рабочая оценка

Это выводы для обсуждения, а не уже принятые архитектурные решения.

- Оба подхода стоит проверять на одинаковых определениях показателей. Иначе сравнение схем смешается с разницей в бизнес-правилах. Основание: согласованное определение выручки выше и контрольные результаты в [вопросах](../tasks.md).
- В проекте нужен явный учёт уровня строки: заказ, позиция, платёж и отзыв имеют разные кратности. Иначе соединения могут размножить суммы. Основание: [структура raw](../../../scripts/init/02_raw_ddl.sql) и предупреждение о соединениях в [вопросах](../tasks.md).
- На этом этапе полезнее фиксировать ключи, кратности, правила пропусков и проверочные запросы каждого подхода, чем писать две полные загрузки. Основание: выбранный пользователем порядок «короткие варианты → выбор → SQL».
