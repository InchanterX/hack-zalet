# Вариант B: аналитические факты и измерения

**Статус:** рассмотренная, но не реализованная альтернатива для личного проекта. Причина выбора варианта A — [D19](decision-log.md#d19-выбор-архитектуры-для-личного-решения). Общие правила: [requirements.md](requirements.md).

**Рабочий промпт для этого эскиза, составленный Codex из согласованных ответов, а не дословная реплика пользователя:** «Предложи аналитическую модель `core` на фактах и измерениях для всех восьми таблиц `raw`. Сохрани атомарные строки, исходные ключи и неполные записи; отдельно рассмотри предрасчёт показателей уровня заказа. Учти определения из `requirements.md`. Дай таблицы, связи, порядок загрузки, путь к пяти ответам и риски без полного SQL». Точные пользовательские формулировки и ответы — в [журнале решений](decision-log.md).

## Идея

Сохранить атомарные события как факты и разнести описательные поля по измерениям. В факте заказа дополнительно хранить заранее агрегированные суммы и количества на уровне заказа. Это моя проектная гипотеза: она упрощает отчёты по заказам, но создаёт повторение вычисленных данных, которое придётся проверять при каждой сборке.

## Предлагаемые таблицы

| Таблица `core` | Уровень и ключ | Источник и причина |
| --- | --- | --- |
| `dim_buyers` | один покупатель, `customer_unique_id` | Устойчивая идентичность для повторных заказов. [D07](decision-log.md#d07-покупатель). |
| `dim_customer_records` | запись покупателя, `customer_id` | Сохраняет исходные местоположение и связь с покупателем для каждого заказа. |
| `dim_products` | товар, `product_id` | Сохраняет все товары и их атрибуты, включая неизвестную категорию. |
| `dim_sellers` | продавец, `seller_id` | Сохраняет местоположение продавца. |
| `dim_categories` | исходный код категории или техническое «Неизвестно» | Объединяет переводы из `raw.product_category_translation`, коды товаров без перевода и явную группу для пустой категории. Код и отображаемое имя хранятся отдельно. [D10](decision-log.md#d10-неизвестные-и-непереведённые-категории). |
| `fact_orders` | заказ, `order_id` | Статус и даты из `raw.orders`, ссылка на `customer_id`; дополнительно суммы товаров, доставки, платежей, число единиц, товарных строк и отзывов. Заказ без позиций сохраняется с нулевыми счётчиками. |
| `fact_order_items` | единица товара, `(order_id, order_item_id)` | Атомарные цены, доставка, срок отгрузки и ссылки на заказ, товар, продавца. [D08](decision-log.md#d08-единица-товара-и-позиция). |
| `fact_payments` | платёж, `(order_id, payment_sequential)` | Атомарные платежи остаются отдельно от суммы товаров. [D11](decision-log.md#d11-платежи-и-расхождения). |
| `fact_reviews` | отзыв, `(review_id, order_id)` | Все отзывы, включая несколько для заказа. [D09](decision-log.md#d09-отзывы). |

Все восемь таблиц `raw` имеют явное назначение: `orders`, `order_items`, `order_payments`, `order_reviews`, `products`, `sellers`, `customers` дают соответствующие факты или измерения; `product_category_translation` наполняет `dim_categories`. Измерение категорий также включает исходные коды из `products`, которые отсутствуют в переводе. Строки переводов сохраняются, даже если товары на них не ссылаются. [D03](decision-log.md#d03-общий-охват-вариантов), [профиль данных](data-profile.md).

## Связи и загрузка

- `fact_orders` имеет ссылку на `dim_customer_records`, откуда доступен `dim_buyers`; `fact_order_items` ссылается на заказ, товар и продавца. Категория товара разрешается через `dim_products → dim_categories`.
- Каждая атомарная таблица хранит исходный ключ. Для производных колонок `fact_orders` происхождение фиксируется формулой: суммы и количества рассчитываются отдельной группировкой каждой дочерней таблицы по `order_id`, затем присоединяются к заказу через `LEFT JOIN`. Это исключает перемножение позиций, платежей и отзывов. [D15](decision-log.md#d15-прослеживаемость-до-источника), [tasks.md](../tasks.md).
- При повторной сборке факты и измерения пересоздаются согласованно в одной транзакции. Некорректные непустые значения вызывают ошибку; пропуски необязательных полей становятся `NULL`. [D13–D14](decision-log.md).
- После загрузки сравниваются агрегаты `fact_orders` с повторным расчётом из атомарных фактов. Расхождение — ошибка проверки модели, а не повод корректировать источник. [D11](decision-log.md#d11-платежи-и-расхождения).

## Как получить пять ответов из `core`

1. **Месяцы:** календарный диапазон присоединить к `fact_orders` по месяцу оформления; число заказов — из `fact_orders`, выручка — сумма `item_price_total` только при `delivered`. Месяц без заказов остаётся. [D05](decision-log.md#d05-выручка).
2. **Продавцы:** группировать `fact_order_items.price` по продавцу через `fact_orders` со статусом `delivered`, затем присоединить `dim_sellers`. Сумму нельзя брать из `fact_orders`: она относится ко всему заказу, где бывают разные продавцы. [tasks.md](../tasks.md).
3. **Средний чек:** усреднить `item_price_total + freight_total` по вручённым строкам `fact_orders`; среднее число строк и единиц взять из агрегированных счётчиков этого же факта. [D16](decision-log.md#d16-средний-чек), [D18](decision-log.md#d18-строка-и-единица-товара).
4. **Повторные заказы:** сгруппировать `fact_orders` по `dim_buyers` для всех статусов и посчитать покупателей с двумя и более заказами. [D17](decision-log.md#d17-повторный-заказ).
5. **Категории:** агрегировать цену атомарных `fact_order_items` во вручённых заказах по коду `dim_categories`; отображать перевод, исходный код или «Неизвестно». Сумму категорий сверить с общей выручкой. [D10](decision-log.md#d10-неизвестные-и-непереведённые-категории).

## Проверяемые последствия

- **Плюс, моя оценка:** показатели уровня заказа читаются из одной строки `fact_orders`, а различие уровней фактов видно в схеме. Это сокращает повторные группировки в текущих отчётах.
- **Цена подхода:** в `fact_orders` дублируются итоги атомарных фактов. Каждая новая загрузка требует сверки этих итогов; новые виды аналитики могут потребовать изменения состава факта. Без правильного порядка агрегации модель сама начнёт размножать деньги. [D12](decision-log.md#d12-критерии-выбора).
- **Критерий опровержения:** если дополнительная сложность сборки и сверки не даёт заметной простоты пяти запросов, предрасчёт не оправдан. Прохождение контролей пока не проверено SQL из `core`.
