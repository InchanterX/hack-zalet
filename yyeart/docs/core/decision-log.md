# Происхождение решений по личной модели `core`

Статус записей ниже: согласованы для подготовки личного варианта; коллективное решение ещё не принято. Исходный запрос и его уточнения сохранены в [рабочих заметках](working-notes.md). `Q1`–`Q12` — вопросы Codex в этой беседе. «Основание» — моя открытая оценка, не слова пользователя.

## D01. Личное решение

- **Вход:** «Нас 5 участников. Наш план - подготовить несколько решений, потом прийти к консенсусу»; затем «мы работаем по-одиночке. мы представляем индивидуальное решение».
- **Ответ:** пользователь подтвердил: «Да, это мой личный проект».
- **Основание:** документы и эскизы описывают один самостоятельный вариант для последующего сравнения с четырьмя другими.

## D02. Порядок работы и число подходов

- **Вход:** Q1 «Подготовить сначала 2–3 коротких варианта `core` (сущности, уровень строк, ключи, правила загрузки), а полный SQL писать после выбора?»; Q4 «Для вашего личного проекта сначала сравнить два подхода: нормализованные сущности и аналитическую модель „факты/измерения“, а третий добавлять только при реальной новой идее?».
- **Ответ:** «Да, сначала 2–3 варианта»; «Да, два подхода сначала».
- **Основание:** два коротких эскиза позволяют проверить различие архитектур без написания двух полных загрузок. Третий имеет смысл при отдельной, проверяемой идее.

## D03. Общий охват вариантов

- **Вход:** Q2 «Требовать от каждого варианта охвата всех восьми `raw`-таблиц и возможности ответить на пять известных вопросов?».
- **Ответ:** «Да, единый охват».
- **Основание:** [задание](../handout.md) перечисляет восемь файлов, а [вопросы](../tasks.md) предупреждают о пяти будущих вопросах. Сравнивать варианты с разным охватом было бы трудно.

## D04. Коллективный выбор после презентаций

- **Вход:** Q3 «Считать решение принятым только при согласии всех пяти, а разногласия сначала проверять на данных и фиксировать письменно?»; затем уточнение о самостоятельной работе каждого участника.
- **Ответ:** «Нет, достаточно большинства».
- **Основание:** для пяти участников простое большинство — минимум `floor(5 / 2) + 1 = 3` голоса. Это относится к будущему обсуждению пяти личных решений.

## D05. Выручка

- **Вход:** Q5 «Зафиксировать для сравнения выручку как сумму `price` позиций заказов со статусом `delivered`, без `freight_value`?».
- **Ответ:** «Да, такое определение».
- **Основание:** при полном проходе исходных CSV такая сумма совпала с контролем `13 221 498.11` в [вопросах](../tasks.md). Поля и статус определены в [структуре raw](../../../scripts/init/02_raw_ddl.sql). В [глоссарии](../../GLOSSARY.md) записан смысл показателя без имён колонок.

## D06. Сохранность неполных записей

- **Вход:** Q6 «Требовать, чтобы модель сохраняла заказы без позиций и товары без категории, явно показывая пробелы в данных?».
- **Ответ:** «Да, сохранять и показывать».
- **Основание:** прямой проход [заказов](../../../data/olist_orders_dataset.csv), [позиций](../../../data/olist_order_items_dataset.csv) и [товаров](../../../data/olist_products_dataset.csv) выявил 775 заказов без позиций и 610 товаров с пустой категорией. Исключение таких строк скрывает качество данных и может менять число заказов или сумму по категориям.

## D07. Покупатель

- **Вход:** Q7 «Называть „покупателем“ сущность с устойчивым `customer_unique_id`, а `customer_id` считать записью покупателя, связанной с заказом?».
- **Ответ:** «Да, закрепить термин».
- **Основание:** [вопросы](../tasks.md) дают контроль 96 096 покупателей и предупреждают, что 99 441 получается при неверном ключе. Оба поля есть в [структуре raw](../../../scripts/init/02_raw_ddl.sql); термин закреплён в [глоссарии](../../GLOSSARY.md).

## D08. Единица товара и позиция

- **Вход:** Q8 «Считать каждую строку `raw.order_items` одной единицей товара, сохраняя `(order_id, order_item_id)` как её исходный ключ; группировку одинаковых товаров делать только для анализа?».
- **Ответ:** «Да, строка = единица».
- **Основание:** [задание](../handout.md) и [структура raw](../../../scripts/init/02_raw_ddl.sql) определяют `order_item_id` как номер позиции внутри заказа. Сохранение исходного уровня позволяет позже группировать одинаковые товары без потери отдельных цен и продавцов.

## D09. Отзывы

- **Вход:** Q9 «Сохранять все отзывы, включая несколько на заказ, и считать исходным ключом пару `(review_id, order_id)`?».
- **Ответ:** «Да, сохранить все отзывы».
- **Основание:** полный проход [CSV отзывов](../../../data/olist_order_reviews_dataset.csv) показал, что `review_id` повторяется, а пары `(review_id, order_id)` уникальны. Сведение к одному отзыву на заказ потеряло бы записи.

## D10. Неизвестные и непереведённые категории

- **Вход:** Q10 «В отчёте по категориям показывать пустую категорию как „Неизвестно“, а категорию без перевода — под исходным названием, чтобы не терять выручку?».
- **Ответ:** «Да, эти правила».
- **Основание:** [вопросы](../tasks.md) требуют, чтобы сумма выручки по категориям совпадала с общей. Явная группа для пустых значений и сохранение исходного названия при отсутствии перевода предотвращают потерю таких продаж.

## D11. Платежи и расхождения

- **Вход:** Q11 «Хранить платежи отдельно от стоимости товаров и не подгонять расхождения; показывать их отдельной проверкой качества данных?».
- **Ответ:** «Да, отдельно и с проверкой».
- **Основание:** [структура raw](../../../scripts/init/02_raw_ddl.sql) допускает несколько платежей по заказу. Сумма платежей и сумма цен позиций относятся к разным источникам; автоматическая подгонка скрыла бы расхождение.

## D12. Критерии выбора

- **Вход:** Q12 «Выбирать итоговую схему прежде всего по корректности пяти ответов, сохранности данных и понятности ключей; удобство запросов и скорость сравнивать после этого?».
- **Ответ:** «Да, такой приоритет».
- **Основание:** [задание](../handout.md) требует работающую модель из `raw` и объяснение её решений; [вопросы](../tasks.md) задают контрольные результаты. Для этой учебной задачи проверяемая корректность важнее микрооптимизации.

## D13. Преобразование типов

- **Вход:** Q13 «Преобразовывать непустые значения в типы `core`, пустые необязательные поля — в `NULL`, а при будущих некорректных непустых значениях прерывать сборку с явной ошибкой?».
- **Ответ:** «Да, явная ошибка».
- **Основание:** [задание](../handout.md) оставляет все исходные поля в `raw` текстовыми и относит приведение типов к построению `core`. Полный проход текущих восьми CSV через `csv.DictReader` с проверкой чисел через `Decimal`/`int`, дат через `datetime.fromisoformat` не выявил некорректных непустых значений в проверенных числовых и временных полях; это свойство текущего снимка, а не будущих загрузок.

## D14. Повторяемая сборка

- **Вход:** Q14 «Требовать один воспроизводимый сценарий сборки `core` из `raw`, который безопасно запускать повторно?».
- **Ответ:** «Да, повторяемая сборка».
- **Основание:** [задание](../handout.md) требует сборку из `raw` на чистой базе. Безопасный повторный запуск делает ту же модель проверяемой после изменения SQL и не зависит от оставшегося состояния прежней попытки.

## D15. Прослеживаемость до источника

- **Вход:** Q15 «Сохранять в `core` исходные ключи строк и таблицу происхождения, чтобы любую запись можно было сверить с `raw`?».
- **Ответ:** «Да, прослеживаемость».
- **Основание:** исходный ключ и имя таблицы-источника позволяют объяснить строку модели и проверить сохранность данных, которой требует [задание](../handout.md). Физический способ хранения этой связи различается между двумя эскизами.

## D16. Средний чек

- **Вход:** Q16 «Определить средний чек как среднюю по вручённым заказам сумму `price + freight_value` всех их единиц товара?».
- **Ответ:** «Да, чек включает доставку».
- **Основание:** сумма товаров и доставки для вручённых заказов в [CSV позиций](../../../data/olist_order_items_dataset.csv), делённая на число вручённых заказов в [CSV заказов](../../../data/olist_orders_dataset.csv), даёт `15 424 463.65 / 96 478 = 159.87545…`, то есть контроль `159.88` в [вопросах](../tasks.md). Выручка из D05 остаётся без доставки.

## D17. Повторный заказ

- **Вход:** Q17 «Для контроля 3,12% считать повторным покупателем того, у кого минимум два заказа любого статуса, и честно назвать метрику „повторные заказы“?».
- **Ответ:** «Да, заказы любого статуса».
- **Основание:** полный проход [CSV покупателей](../../../data/olist_customers_dataset.csv) и [CSV заказов](../../../data/olist_orders_dataset.csv) дал `2 997 / 96 096 × 100 = 3.1188…%`, то есть контроль `3,12%` в [вопросах](../tasks.md). Только вручённые заказы дали `2 801 / 93 358 × 100 = 3.0003…%`. Термин «повторный заказ» не приписывает отменённому заказу факт покупки.

## D18. Строка и единица товара

- **Вход:** Q18 «В среднем числе строк считать одну строку на сочетание `(order_id, product_id, seller_id)`, а единицы — исходные записи `order_items`?».
- **Ответ:** «Да, различать строку и единицу».
- **Основание:** полный проход [CSV позиций](../../../data/olist_order_items_dataset.csv) для вручённых заказов дал `100 196` сочетаний товара и продавца и `110 197` единиц на `96 478` заказов: `1.04` строки и `1.14` единицы на заказ после округления до двух знаков. Понятия добавлены в [глоссарий](../../GLOSSARY.md).

## D19. Выбор архитектуры для личного решения

- **Вход:** пользователь: «согласно документации, выполни задание» после подготовки [двух эскизов](comparison.md).
- **Выбор Codex:** реализовать [нормализованный вариант A](proposal-normalized.md) как личное решение. Пользователь не выбирал его отдельным сообщением; коллективного решения пока нет.
- **Основание:** по согласованным [критериям D12](#d12-критерии-выбора) вариант A сохраняет исходные уровни и ключи без предрассчитанных денежных итогов. Вариант B потребовал бы хранить и сверять производные суммы заказа, тогда как вопросы о продавцах и категориях всё равно читают атомарные позиции. Подробности — в [сравнении](comparison.md) и [ADR-0001](../adr/0001-normalized-core.md).

## Как проверить упомянутые факты о CSV

Следующие запросы проверяют исходные данные после загрузки в `raw`; ответы на аналитические вопросы должны считаться из будущей модели `core` согласно [заданию](../handout.md).

```sql
SELECT count(*)
FROM raw.orders o
WHERE NOT EXISTS (SELECT 1 FROM raw.order_items i WHERE i.order_id = o.order_id);

SELECT count(*)
FROM raw.products
WHERE nullif(trim(product_category_name), '') IS NULL;

SELECT count(*) AS rows,
       count(DISTINCT (review_id, order_id)) AS unique_pairs,
       count(DISTINCT review_id) AS unique_review_ids
FROM raw.order_reviews;

SELECT sum(i.price::numeric)
FROM raw.order_items i
JOIN raw.orders o ON o.order_id = i.order_id
WHERE o.order_status = 'delivered';

WITH item_totals AS (
  SELECT order_id, sum(price::numeric + freight_value::numeric) AS amount
  FROM raw.order_items
  GROUP BY order_id
), payment_totals AS (
  SELECT order_id, sum(payment_value::numeric) AS amount
  FROM raw.order_payments
  GROUP BY order_id
)
SELECT count(*) AS differing_orders
FROM item_totals i
JOIN payment_totals p USING (order_id)
WHERE i.amount <> p.amount;
```
