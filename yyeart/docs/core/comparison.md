# Сравнение двух подходов

Сравниваются [нормализованный вариант A](proposal-normalized.md) и [аналитический вариант B](proposal-dimensional.md) по одному [контракту](requirements.md). Это предварительная инженерная оценка Codex, а не утверждённое решение участника или команды. Происхождение правил и критериев — [журнал решений](decision-log.md), прежде всего [D02](decision-log.md#d02-порядок-работы-и-число-подходов) и [D12](decision-log.md#d12-критерии-выбора).

| Критерий | A: нормализованный | B: факты и измерения | Вывод сейчас |
| --- | --- | --- | --- |
| Пять контрольных ответов | Реализованные [SQL-запросы](../../model/answers) дали контрольные результаты из [tasks.md](../tasks.md). | Путь запросов описан, SQL для B не реализован. | A проверен на текущем снимке; B остаётся эскизом. |
| Сохранность восьми источников | У каждого источника есть близкая к исходной таблица; `buyers` вычисляется дополнительно. | Атомарные факты и измерения сохраняют источники; категории собираются из перевода и кодов товаров. | Оба покрывают источники на уровне эскиза; A проще сверять по числу строк. |
| Ключи и происхождение | Исходные ключи являются ключами атомарных таблиц. | Исходные ключи сохранены в фактах и измерениях; агрегаты `fact_orders` требуют отдельной формулы сверки. | A проще объяснить построчно. |
| Неполные записи | Заказ без позиций и товар без категории остаются в своих таблицах. | Заказ остаётся в `fact_orders` с нулевыми счётчиками; неизвестная категория требует явной строки измерения. | Оба возможны, B требует больше правил загрузки. |
| Выручка продавца и категории | Агрегация атомарных позиций с нужными соединениями. | Та же атомарная агрегация; предрасчёт заказа не заменяет её. | B здесь почти не сокращает запросы. |
| Средний чек и числа единиц | Нужна группировка позиций до уровня заказа. | Предрассчитанные суммы и количества лежат в `fact_orders`. | B удобнее для этих отчётов, если сверка агрегатов работает. |
| Повторяемая сборка | Зависимости в основном между исходными сущностями. | Дополнительно нужно согласованно пересчитать и проверить агрегаты заказа. | A проще пересобирать и проверять. |
| Неизвестные будущие вопросы | Атомарные источники доступны для новых срезов. | Атомарные факты тоже доступны; новые готовые показатели могут потребовать изменить `fact_orders`. | Преимущество A в меньшем числе производных полей; точную пользу B пока нельзя проверить. |
| Скорость | Не измерена. | Не измерена. | Нужны реальный SQL и `EXPLAIN`; вывод о скорости преждевременен. |

## Моя предварительная рекомендация

**Вариант A** соответствует принятому порядку приоритетов: сначала проверяемые ответы, сохранность строк и понятные ключи, затем удобство запросов и скорость ([D12](decision-log.md#d12-критерии-выбора)). Его реализация прошла [сверку исходных строк](../../model/validate_core.sql) и пять [контрольных запросов](answers.md). Вариант B предрассчитывает итоги заказа, но для выручки продавцов и категорий всё равно нужны атомарные позиции. Для текущего [снимка данных](data-profile.md) это добавило бы обязательную сверку без доказанной необходимости. B остаётся непроверенным эскизом.

## Что может изменить оценку

1. Реализованный B проходит все [контроли](requirements.md#контрольные-результаты), сохраняет строки и делает существенно проще повторяющиеся запросы без ошибок сверки агрегатов.
2. Новые вопросы требуют преимущественно аналитики на уровне заказа и редко обращаются к атомарным событиям. Их содержание пока не опубликовано в [tasks.md](../tasks.md).
3. Измерения на реальном SQL показывают значимый выигрыш B, который оправдывает стоимость дополнительных агрегатов. Сейчас таких измерений нет.

## Решение после просмотра

**Выбранный подход для личного решения:** A, нормализованный. Решение Codex по запросу выполнить задание; команда из пяти участников его ещё не обсуждала. [D19](decision-log.md#d19-выбор-архитектуры-для-личного-решения), [ADR-0001](../adr/0001-normalized-core.md).

Причина выбора записана в [ADR-0001](../adr/0001-normalized-core.md). Сравнение остаётся доступным для последующего объединения личных решений.
