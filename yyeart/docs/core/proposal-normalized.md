# Вариант A: нормализованная модель источников

**Статус:** выбран и реализован для личного проекта в [build_core.sql](../../model/build_core.sql); коллективное решение ещё не принималось. Основание выбора — [D19](decision-log.md#d19-выбор-архитектуры-для-личного-решения). Общие правила: [requirements.md](requirements.md).

**Рабочий промпт для этого эскиза, составленный Codex из согласованных ответов, а не дословная реплика пользователя:** «Предложи нормализованную модель `core` для всех восьми таблиц `raw`. Сохрани исходные ключи и неполные записи, раздели сущности разных уровней, учти определения показателей из `requirements.md`. Дай таблицы, связи, порядок загрузки, путь к пяти ответам и риски без полного SQL». Точные пользовательские формулировки и ответы — в [журнале решений](decision-log.md).

## Идея

В `core` хранить отдельные сущности заказа, покупателя, товара, продавца, платежа, отзыва и перевода категории. Денежные итоги не дублировать: вычислять их из атомарных позиций, группируя до соединения с платежами или отзывами. Это моя проектная гипотеза, основанная на разных уровнях строк в [DDL raw](../../../scripts/init/02_raw_ddl.sql) и риске размножения сумм, указанном в [tasks.md](../tasks.md).

## Предлагаемые таблицы

| Таблица `core` | Уровень и ключ | Источник и причина |
| --- | --- | --- |
| `buyers` | один покупатель, `customer_unique_id` | Выделяет устойчивую идентичность из `raw.customers` для повторных заказов. [D07](decision-log.md#d07-покупатель). |
| `customer_records` | одна запись покупателя, `customer_id` | Сохраняет все исходные адресные поля и связь с `buyers`; не выбирает произвольный «текущий» адрес. |
| `orders` | один заказ, `order_id` | Сохраняет статус и временные метки, в том числе заказы без позиций. [D06](decision-log.md#d06-сохранность-неполных-записей). |
| `order_items` | одна единица товара, `(order_id, order_item_id)` | Сохраняет `product_id`, `seller_id`, `price`, `freight_value`, срок отгрузки. [D08](decision-log.md#d08-единица-товара-и-позиция). |
| `payments` | один платёж, `(order_id, payment_sequential)` | Сохраняет способ, рассрочку и сумму отдельно от цены товара. [D11](decision-log.md#d11-платежи-и-расхождения). |
| `reviews` | один отзыв, `(review_id, order_id)` | Сохраняет несколько отзывов на заказ. [D09](decision-log.md#d09-отзывы). |
| `products` | один товар, `product_id` | Сохраняет исходный код категории и атрибуты, включая пустые значения категории. [D06](decision-log.md#d06-сохранность-неполных-записей). |
| `sellers` | один продавец, `seller_id` | Сохраняет город, штат и почтовый префикс продавца для вопроса о выручке. |
| `category_translations` | один перевод, `product_category_name` | Сохраняет все строки справочника; отсутствие перевода у товара не удаляет товар. [D10](decision-log.md#d10-неизвестные-и-непереведённые-категории). |

Каждая исходная таблица имеет соответствующую атомарную таблицу `core`; `buyers` — дополнительная сущность из `raw.customers`. Исходные ключи остаются в именованных столбцах, а таблица-источник однозначно задана соответствием выше. Для `buyers` путь назад идёт через `customer_records`. Это предложенный способ выполнить [D15](decision-log.md#d15-прослеживаемость-до-источника).

## Связи и загрузка

- `buyers 1 → N customer_records`; `customer_records 1 → N orders` в схеме, даже если текущие CSV дают одну запись на заказ. Так не кодируется случайное свойство текущей выгрузки как бизнес-закон.
- `orders 1 → N order_items`, `orders 1 → N payments`, `orders 1 → N reviews`. Ноль дочерних строк допустим и виден в проверках.
- `order_items` ссылается на `products` и `sellers`. `products.product_category_name` остаётся исходным кодом; перевод присоединяется опционально по коду, поэтому отсутствие перевода не уничтожает товар.
- Перезапуск собирает только принадлежащие скрипту таблицы `core` в одной транзакции. Непустые типизированные значения преобразуются; пустые необязательные поля становятся `NULL`; ошибки типов и отсутствующие обязательные ссылки останавливают сборку с сообщением. [D13–D14](decision-log.md).

## Как получить пять ответов из `core`

1. **Месяцы:** создать диапазон 24 месяцев, отдельно агрегировать заказы по месяцу оформления и `price` вручённых позиций, затем присоединить оба итога к календарю. Это сохраняет месяц без заказов. [D05](decision-log.md#d05-выручка), [tasks.md](../tasks.md).
2. **Продавцы:** сгруппировать `order_items.price` по `seller_id` только для вручённых заказов; затем присоединить `sellers`. Число заказов — `count(DISTINCT order_id)`, единиц — `count(*)`.
3. **Средний чек:** сначала сгруппировать позиции по `order_id` и получить сумму `price + freight_value`, число единиц и число разных `(product_id, seller_id)`; затем усреднить по вручённым заказам, включая заказ с нулём позиций, если он есть. [D16](decision-log.md#d16-средний-чек), [D18](decision-log.md#d18-строка-и-единица-товара).
4. **Повторные заказы:** посчитать число `orders` на `customer_unique_id` через `customer_records` для всех статусов; повторный покупатель имеет минимум два заказа. [D17](decision-log.md#d17-повторный-заказ).
5. **Категории:** позиции вручённых заказов соединить с `products`, перевод — через `LEFT JOIN`; группировать по исходному коду категории, а отображаемое имя выбирать из перевода, исходного кода и «Неизвестно». Сумму категорий сверить с общей выручкой. [D10](decision-log.md#d10-неизвестные-и-непереведённые-категории).

## Проверяемые последствия

- **Плюс, моя оценка:** атомарные таблицы близки к исходным данным, поэтому сохранность и прослеживаемость проще проверить по ключам и числу строк. [Профиль](data-profile.md), [D12](decision-log.md#d12-критерии-выбора).
- **Цена подхода:** аналитические запросы делают больше соединений и группировок. Соединять позиции, платежи и отзывы напрямую в одном запросе нельзя: кратности умножат суммы; сначала нужны отдельные агрегаты на уровне заказа. [DDL raw](../../../scripts/init/02_raw_ddl.sql), [tasks.md](../tasks.md).
- **Проверка реализации:** пять [запросов](../../model/answers) дали контрольные результаты, а [сверка](../../model/validate_core.sql) показала совпадение числа строк каждого источника с атомарной таблицей `core`. Новые вопросы могут изменить оценку пригодности схемы.
